# US 8.5 — Gestion base d'aliments (admin) — Plan d'implémentation

> **Pour exécuteur agentique** : implémenter tâche par tâche, TDD (test rouge → code → vert),
> commits fréquents. Cases `- [ ]` = suivi.

**Objectif** : espace admin « Aliments » — lister / rechercher / créer / éditer / archiver les
aliments éditoriaux (`owner_id NULL`, `source library`), macros + 10 micros. Miroir du CRUD exos (8.2).

**Architecture** : validateur de formulaire **pur** dans `@wellness/shared` (testé) ; couche
`data/foods.ts` étendue (supabase-js, RLS = frontière) ; 2 écrans admin + routing réorganisé
(liste = hub, import déplacé). Migration RLS d'écriture éditoriale foods (checkpoint 🔴, débloque 8.6 aussi).

**Stack** : React + Vite + react-router (admin), supabase-js, Zod (shared), Vitest.

**Spec** : [docs/specs/functional/us/8.5-gestion-aliments.md](../specs/functional/us/8.5-gestion-aliments.md).

## Notes de conception

- **Pourquoi insert/update séparés (pas upsert) à l'édition** : l'upsert réécrirait `portions` /
  `import_key` / `barcode` (non présents dans le formulaire) avec des valeurs par défaut. Un `update`
  ciblé ne touche que les colonnes éditées.
- **RLS = frontière** : la couche data envoie `owner_id: null` ; seule la migration RLS (is_content_editor)
  autorise l'écriture. Un rôle non éditeur voit la nav masquée **et** est refusé côté base.
- **Pas de `status`** sur les aliments : pas de bouton publier/brouillon (différence avec les exos).
- **DRY** : réutiliser les styles d'`ExercisesScreen`/`ExerciseEditScreen` (ne pas diverger le thème).
