## ⚠️ Hypothèses à confirmer par Florian/Damien (à la validation du plan)

Le modèle de données actuel ne couvre pas deux points de la spec ; on retient des hypothèses MVP explicites :

- **H1 — « Séance du jour » sans planning hebdo.** Les programmes ont des séances **ordonnées** (`orderIndex`) mais **aucun jour de semaine**. → Le widget affiche la **prochaine séance non terminée** du programme muscu actif (par ordre), pas une séance datée. Libellé : « Séance {N} · {nom} » (jamais un jour de semaine). Un `workout` `active` prime (CTA « Reprendre »). Le vrai planning calendaire est une **US ultérieure**.
- **H2 — Jour actif nutrition = ≥ 1 repas saisi ce jour** (au moins une entrée `food_entries` avec kcal > 0). La règle stricte « tous les repas configurés saisis » nécessite une donnée de créneau-repas non exploitable aujourd'hui → **différée**.
- **H3 — Pas de « jour de repos neutre »** au MVP (impossible sans planning). Streak = nb de jours **actifs consécutifs** en remontant depuis aujourd'hui ; le jour courant pas encore actif **ne casse pas** la série tant que la journée n'est pas finie (on compte la plus longue suite se terminant aujourd'hui **ou** hier). Repos-neutre rebranché avec le planning (H1).

- **H4 — Widget Poids affiché quand le pilier `nutrition` est actif.** Le suivi du poids (pesée + courbe) vit aujourd'hui dans l'espace nutrition (`nutrition-stats`) → on conditionne le widget Poids au pilier `nutrition`. Si le poids devient un suivi indépendant plus tard, on rebranchera (afficher dès qu'il existe ≥ 1 pesée).

Si Florian préfère un autre arbitrage (ex. masquer « Séance du jour » tant qu'il n'y a pas de planning), on ajuste le plan avant code.

## Conventions de dates (important pour le streak)

- **Nutrition & poids** : colonne `log_date` en **date locale `AAAA-MM-JJ`**.
- **Séances & courses** : `started_at`/`finished_at` en **timestamp UTC ISO**.
- → `computeStreak` travaille sur des **clés de date locale** (`AAAA-MM-JJ`). La conversion UTC→date locale se fait **côté mobile** (dans le hook d'agrégation) avant d'alimenter la fonction pure. Un helper `localDayKey(date)` (format `AAAA-MM-JJ` à partir de l'heure locale) est ajouté dans `@wellness/shared` et réutilisé (il existe déjà une version app-locale dans `nutrition-stats.tsx` — on la centralise).

```ts
/** Clé de jour local AAAA-MM-JJ (pour agréger séances/courses UTC et journées nutrition/poids locales). */
export function localDayKey(d: Date): string {
  const pad = (n: number) => String(n).padStart(2, '0');
  return `${d.getFullYear()}-${pad(d.getMonth() + 1)}-${pad(d.getDate())}`;
}
```

### Task 2 : `computeStreak` + type `DayActivity`

**Files:** Create `packages/shared/src/streak.ts` (+ `.test.ts`) ; MAJ `index.ts`.

Contrat (MVP, cf. H2/H3) :
- Entrée : un **ensemble de clés de jours actifs** (`Set<string>` ou `string[]` de `AAAA-MM-JJ`) + la **clé du jour courant** (`todayKey`, passée en paramètre — **pas** de `new Date()` dans shared, pour rester pur/testable).
- Sortie : `{ current: number; activeToday: boolean }` — `current` = longueur de la suite de jours actifs consécutifs se terminant à `today` **ou** `yesterday` (si aujourd'hui pas encore actif, on ne casse pas). `activeToday` = today ∈ actifs.

- [ ] **Tests rouges** (couvrant : suite simple, trou qui casse, aujourd'hui inactif mais hier actif → série conservée, aucun jour → 0, doublons ignorés) :
```ts
import { computeStreak } from './streak';
describe('computeStreak', () => {
  const days = (arr: string[]) => new Set(arr);
  it('compte les jours actifs consécutifs finissant aujourd’hui', () => {
    expect(computeStreak(days(['2026-07-09','2026-07-10','2026-07-11']), '2026-07-11'))
      .toEqual({ current: 3, activeToday: true });
  });
  it('aujourd’hui inactif mais hier actif → série conservée (finit hier)', () => {
    expect(computeStreak(days(['2026-07-09','2026-07-10']), '2026-07-11'))
      .toEqual({ current: 2, activeToday: false });
  });
  it('trou casse la série', () => {
    expect(computeStreak(days(['2026-07-07','2026-07-10','2026-07-11']), '2026-07-11'))
      .toEqual({ current: 2, activeToday: true });
  });
  it('ni aujourd’hui ni hier → 0', () => {
    expect(computeStreak(days(['2026-07-01']), '2026-07-11'))
      .toEqual({ current: 0, activeToday: false });
  });
  it('aucun jour → 0', () => {
    expect(computeStreak(days([]), '2026-07-11')).toEqual({ current: 0, activeToday: false });
  });
});
```
- [ ] **Impl** : itérer en arrière depuis `today` : si today actif, partir de today ; sinon si yesterday actif, partir de yesterday ; sinon 0. Compter tant que le jour précédent est dans le set. Helper interne **DST-safe** via `Date.UTC` (jamais `new Date(key)` + `.setDate` sur un objet local) :
```ts
/** Jour précédent d'une clé AAAA-MM-JJ, arithmétique en UTC (insensible au DST). */
function prevKey(key: string): string {
  const [y, m, d] = key.split('-').map(Number);
  const t = Date.UTC(y, m - 1, d) - 86_400_000;
  const p = new Date(t);
  const pad = (n: number) => String(n).padStart(2, '0');
  return `${p.getUTCFullYear()}-${pad(p.getUTCMonth() + 1)}-${pad(p.getUTCDate())}`;
}
```
`computeStreak` : `start = today ∈ set ? today : (prevKey(today) ∈ set ? prevKey(today) : null)` ; si `null` → `{current:0, activeToday: today ∈ set}` ; sinon compter en remontant via `prevKey` tant que dans le set. `activeToday = today ∈ set`.
- [ ] **Type** `DayActivity` exporté (pour typer l'agrégation mobile) : `type DayActivity = { day: string; strength: boolean; running: boolean; nutrition: boolean }` + un helper `activeDayKeys(activities: DayActivity[]): Set<string>` (jour actif = `strength || running || nutrition`). Tester `activeDayKeys`.
- [ ] Vérifier vert, exporter. **Commit** : `feat(shared): computeStreak + DayActivity (règles streak MVP, pur & testé)`

## Phase B — Hooks d'agrégation mobiles

### Task 3 : `dashboard-repository.ts` — hooks réactifs

**Files:** Create `apps/mobile/src/data/repositories/dashboard-repository.ts`.

Réutilise UNIQUEMENT des hooks/fonctions existants (voir spec §1 & recon). Aucun accès SQL direct nouveau si un hook existe déjà.

- [ ] **`useNextSession()`** (widget 7.4, cf. H1) — **règle MVP définitive** : `useActiveWorkout()` → si un workout est `active`, retourner `{ state: 'active-workout', workoutId }` (prime sur tout). Sinon `useActiveProgram('strength')` → si programme actif, `useProgramDetail(program.id)` → retourner **la séance d'`orderIndex` minimum** (`sessions[0]`), **sans condition d'achèvement** (le suivi « séance terminée » par séance n'existe pas au modèle → différé). Sinon `{ state: 'no-program' }`. Retour : `{ state: 'active-workout' | 'has-session' | 'no-program', session?: {name, index, exerciseCount}, workoutId?, isLoading }`. `exerciseCount = session.plans.length`.
- [ ] **`useStreakData(windowDays = 30)`** (widget 7.6) : `sinceKey = localDayKey(d)` où `d` = aujourd'hui décrémenté de `windowDays` jours via `new Date(); d.setDate(d.getDate() - windowDays)` (arithmétique locale, DST-safe car on ne reformate que la date). Agrège en `DayActivity[]` sur cette fenêtre :
  - séances : `useWorkoutHistory()` → pour chaque `finishedAt != null`, `localDayKey(new Date(finishedAt))` → `strength = true`.
  - courses : `useRunHistory()` → idem sur `finishedAt` → `running = true`.
  - nutrition : `useDailyTotals(sinceKey)` → pour chaque `total.kcal > 0`, `day = total.logDate` → `nutrition = true` (H2).
  - Fusionner par clé de jour, renvoyer `{ activities: DayActivity[], streak: computeStreak(activeDayKeys(activities), localDayKey(new Date())), last7: DayActivity[] (L→D de la semaine courante), isLoading }`.
- [ ] **`useNutritionSummary()`** (widget 7.5) : `useDailyTotals(todayKey)` (aujourd'hui) → total du jour ; `useNutritionProfile()` + `useProfile()` → objectif via `tdee(...)` + `targetCalories(...)` (+ `trainingDayCalories` si applicable — MVP : sans détection jour d'entraînement, utiliser l'objectif de base ; bonus jour d'entraînement **différé**). Retour : `{ kcal, target, macros:{p,g,l}, hasProfile, isLoading }`.
- [ ] Typecheck. **Commit** : `feat(mobile): hooks dashboard (next session, streak data, nutrition summary)`
