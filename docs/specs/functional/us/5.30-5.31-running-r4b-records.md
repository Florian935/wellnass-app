# US Running R4b — Records d'allure + mise à jour auto de l'allure de référence

> Deuxième incrément de **R4** (après R4a historique/stats). Couvre **5.30 (records personnels
> d'allure)** et **5.31 (maj auto de l'allure de référence)**. Records = **meilleur segment glissant**
> calculé depuis les traces GPS, **persistés** dans une nouvelle table. Réf. fonctionnelle :
> [running.md](../running.md) §6.4 + §7 + §8. Branche : `feature/running-r4b-records` ·
> Date : 12/07/2026 · **Statut : à valider (pas de code avant validation).**

## 0. Contexte

Le pilier running a : tracker GPS (R1), carte (R2), profil + allures (R3a), programmes (R3b),
planning (R3c-i), historique + stats + courbe d'allure (R4a). Les courses sont dans **`runs`**
(`source`, `gps_track` encodé `{lat, lng, t}` où `t` = secondes depuis le départ, `distance_m`,
`avg_pace_s_per_km`…). L'écran **résumé** (`run/summary?id=`) sert de détail par id.

**Ce qui manque** : aucun record d'allure. La table `personal_records` est **taillée muscu**
(`exercise_id NOT NULL → exercises`, `type in (max_weight/estimated_1rm/best_volume)`, `weight_kg`,
`workout_id`) — **inutilisable** pour des records d'allure par distance. **Aucune infra de
notification** n'existe (`expo-notifications` absent ; les records muscu s'affichent in-app, sans
notification poussée).

Décisions de cadrage (12/07/2026) :
- **Stockage** : **nouvelle table dédiée `running_pace_records`** (migration → **checkpoint 🔴 cloud**,
  comme R3a/R3b-i/R3c-i). Source de vérité pour l'affichage + détection à la fin de course.
- **Célébration** : **animation/bandeau in-app** sur l'écran résumé (aucun module natif, **pas de
  build**). Les **notifications poussées sont différées** (incrément « notifications » dédié, couvrira
  aussi muscu).
- **Distances** : **1 / 5 / 10 km, semi (21 097,5 m), marathon (42 195 m)**.
- **Détection** : à la **fin de course** (flux résumé), sur les **courses GPS terminées uniquement**
  (manuel exclu — données non vérifiables, spec §8).

## 1. Périmètre à livrer

- **Table `running_pace_records`** (1 ligne par (utilisateur, distance)) + migration + RLS + sync + schéma PowerSync.

- **Détection + persistance à la fin de course** : recalcul des meilleurs segments de la course,

- **Backfill** : peuplement initial depuis les courses GPS terminées existantes (historique pré-R4b).
- **Affichage** : **section « Records »** dans l'écran Historique (R4a) — meilleure allure + date par
  distance, tap → course.
- **Célébration in-app** sur le résumé quand un ou plusieurs records tombent.
- i18n `running.records.*` FR/EN.

**Hors périmètre :**
- **Notification poussée** (local/push) → incrément « notifications » dédié (nécessite `expo-notifications` → build).
- **Dénivelé** (5.32), **export GPX** (5.33), **découpage par type** → différés / autres incréments.

- **Édition manuelle** d'un record ; suppression/reset des records (YAGNI).

## 2. Comportement attendu

1. **Fin d'une course GPS** : au résumé, l'app calcule les meilleurs segments de la course pour chaque
   distance atteignable ; tout segment **plus rapide** que le record stocké (ou en l'absence de record)
   devient le **nouveau record** (persisté avec la course + horodatage). Une **célébration in-app**
   (bandeau/animation « Nouveau record ! » listant les distances battues) s'affiche. Si le **5 km** est
   battu, l'**allure de référence** du profil est mise à jour (allure du meilleur segment 5 km).
2. **Course en mode manuel** (sans GPS) : **exclue** des records (aucune trace vérifiable) — aucune
   détection, aucune célébration.
3. **Section « Records »** (écran Historique) : les 5 distances, chacune avec la **meilleure allure**
   (dérivée `temps / distance`), la **date**, et un **tap → détail de la course** (`run/summary?id=`).
   « — » si aucun record pour la distance. Réactif.
4. **Backfill** : si la table est vide (première utilisation post-R4b), l'app peuple les records depuis
   les **courses GPS terminées existantes** (sans célébration).
5. **Offline-first** ; réactif (`useQuery`).

## 3. Règles métier

- **Meilleur segment glissant** : pour une distance cible D, le record est le **temps minimal** d'un
  sous-segment **continu** de la trace couvrant **au moins D** mètres (fenêtre glissante). Un record
  5 km peut être établi au sein d'un 12 km (spec §6.4). Si la trace fait moins de D → **pas de record**
  pour cette distance.
- **Périmètre du calcul = une seule course** : `t` est le temps **depuis le départ de la course**
  (remis à 0 à chaque course, `GpsPoint.t`). Un segment n'a donc de sens **qu'au sein d'une même
  trace** — les records sont des meilleurs segments **par course**, **jamais** un segment à cheval sur
  deux courses.
- **Point de franchissement** : quand la distance cumulée franchit D **entre deux points GPS**, le
  temps du segment est obtenu par **interpolation linéaire de `t` à exactement D** (les deux points
  encadrants donnent la distance et le Δt). Le repli « premier point ≥ D » n'est retenu **que** si une
  contrainte op-sqlite/perf l'impose (à justifier au plan) — l'interpolation est le défaut (évite de
  surévaluer le temps sur GPS clairsemé et de masquer un vrai record).
- **Composition avec le filtre d'outliers** : la distance cumulée applique la **même règle** que
  `totalDistance` (segment dont la vitesse implicite > `MAX_PLAUSIBLE_SPEED_MS` → contribue **0 mètre**),
  **sans** retirer le point du tableau : la **fenêtre temporelle** (`t`) reste cohérente.
- **Distances** (mètres) : `1k`=1000, `5k`=5000, `10k`=10000, `semi`=21097.5, `marathon`=42195.
- **Allure affichée** : dérivée = `best_time_seconds / (D/1000)` s/km, formatée via `useUnits`.
- **Battu** = temps strictement inférieur au record stocké (`<`), ou aucun record existant. Égalité →
  pas de nouveau record (pas de re-célébration).
- **Idempotence** : la détection à la fin est idempotente (upsert « seulement si meilleur »). La
  **non-re-célébration** est garantie par ce fait — à toute visite ultérieure du résumé,
  `detectAndStoreRunRecords` renvoie une liste **vide** (rien n'est plus strictement meilleur) donc pas
  de bandeau. **Aucun drapeau « déjà célébré » persistant n'est nécessaire** ; la garde au montage
  (ref/état) ne sert qu'à éviter un **double appel/flash dans un même rendu**.
- **Manuel exclu** : `source='manual'` (ou trace absente/vide) → jamais de record (spec §8).
- **Filtrage GPS** : réutilise le filtrage d'outliers de vitesse existant (`MAX_PLAUSIBLE_SPEED_MS`)
  pour ne pas fausser un segment par un artefact.
- **Maj allure de réf (5.31)** : uniquement si le **5 km** est battu → `ref5kPaceSPerKm` = allure du
  nouveau meilleur segment 5 km. N'écrase jamais les autres champs du profil.
- **Un record par distance et par utilisateur** (contrainte unique `(user_id, distance_key)`).

## 4. Architecture

- **Migration (🔴 cloud)** : `supabase/migrations/20260712120000_running_pace_records.sql`
  (timestamp **> `20260712110000`** R3c-i) : table `public.running_pace_records`
  (`id uuid pk`, `user_id uuid not null → auth.users on delete cascade`,
  `distance_key text not null check (distance_key in ('1k','5k','10k','semi','marathon'))`,
  `best_time_seconds integer not null`, `run_id uuid not null → public.runs (id) on delete cascade`,
  `achieved_at timestamptz not null`, conventions `created_at/updated_at/deleted_at`,
  **index unique partiel `(user_id, distance_key) where deleted_at is null`** (forme retenue, cohérente
  avec les tables portant `deleted_at` ; cible du conflit d'upsert),
  trigger `set_updated_at`, `alter publication powersync add table`, **RLS** `user_id = auth.uid()`
  (select/insert/update — pas de delete, soft delete). Aucune nouvelle sync rule structurelle : ajouter
  la table au bucket **`user_data`**.
- **Schéma PowerSync local** (`schema.ts`) : déclarer `running_pace_records`
  (`user_id`/`distance_key`/`run_id`/`achieved_at` text, `best_time_seconds` integer, + conventions) +
  l'enregistrer dans `AppSchema`.
- **`@wellness/shared`** (TDD, pur) — `pace-records.ts` :
  - `RUNNING_RECORD_DISTANCES: { key, meters }[]` (les 5 ci-dessus).
  - `bestSegmentTime(points, targetDistanceM): number | null` — **fenêtre glissante deux-pointeurs**
    sur la distance cumulée (haversine, mêmes règles d'outliers que `totalDistance` : segment trop
    rapide → 0 mètre, point conservé) et le temps `t` ; temps minimal pour couvrir ≥ D avec
    **interpolation linéaire de `t` au franchissement de D** (défaut, cf. §3) ; `null` si trace trop
    courte.
  - `computeRunRecords(points): Record<distanceKey, number>` — meilleurs temps par distance atteignable.
  - Tests : trace courte, un point, segment optimal au milieu, outliers, distances exactes.
- **Repository** (`running-record-repository.ts` **ou** extension de `run-repository.ts` — à trancher
  au plan ; préférer un fichier dédié pour ne pas alourdir `run-repository`) :
  - `useRunningRecords(): { records: RunningPaceRecord[]; isLoading }` — lecture réactive de la table
    (5 distances, avec run + date), pour la section « Records ».
  - `detectAndStoreRunRecords(runId): Promise<DistanceKey[]>` — lit `runs` (GPS terminée, sinon no-op),
    décode `gps_track`, `computeRunRecords`, compare à la table, **upsert** les battus (run_id +
    `achieved_at`), maj `ref5kPaceSPerKm` si 5 km battu, retourne les distances battues. **Idempotent**.
  - `backfillRunningRecords(): Promise<void>` — scan des courses GPS terminées, upsert des meilleurs
    (sans célébration). Déclenché **une fois** au montage de la section Records **uniquement lorsque la
    lecture réactive a résolu et que la table est vide** (`!isLoading && records.length === 0`, pas
    « vide » transitoire pendant le chargement). **Idempotent** et **sûr en concurrence** avec
    `detectAndStoreRunRecords` (les deux sont des upserts « seulement si meilleur », même cible
    `unique(user_id, distance_key)`) ; protéger d'un double-lancement par un **drapeau in-flight**
    (module-level).
  - Écritures via helpers `_sql` (offline-first ; upsert = SELECT existant puis insert/patch, ou
    `ON CONFLICT` local — à trancher au plan selon le support op-sqlite).
- **Écrans** :
  - **Section « Records »** dans `running-history/index.tsx` (R4a) : 5 lignes distance → allure/date,
    tap → `run/summary?id=`. État « — » si pas de record. Backfill au montage si vide.
  - **Célébration** dans `run/summary.tsx` : appeler `detectAndStoreRunRecords(id)` **une fois** au
    montage (garde anti-double via un ref/état) ; si des distances sont battues → **bandeau/animation
    in-app** « Nouveau record ! » (RN `Animated`, aucun module natif) + mention de la maj d'allure réf.
- **i18n** FR+EN : `running.records.{ title, sectionTitle, none, distance1k, distance5k, distance10k,
  distanceSemi, distanceMarathon, newRecordTitle, newRecordBody, refPaceUpdated }` (+ réutilise les
  formats d'allure). Parité, aucune chaîne/unité en dur.
