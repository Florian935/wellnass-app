## 0. Contexte

Le pilier running a déjà : le tracker GPS (R1), la carte (R2), le profil + allures (R3a), les programmes
(R3b), le planning daté (R3c-i). Les courses sont enregistrées dans la table **`runs`**
(`source`, `started_at`, `finished_at`, `duration_seconds`, `distance_m`, `avg_pace_s_per_km`,
`gps_track` encodé lat/lng/t, `rpe`, `notes`). L'écran **résumé** (`run/summary?id=<runId>`) sert déjà
de **détail d'une course par id** (`useRun(id)` → carte + splits par km + feedback).

**Ce qui manque** : aucun **écran** ne liste l'historique des courses. Le hook `useRunHistory` existe et
**alimente déjà le dashboard** (`useIsTrainingDay` + `useStreakData` dans `dashboard-repository.ts`, qui
n'en consomment que `finishedAt`) — mais aucun écran de liste n'existe, et il n'y a ni statistiques ni
courbe de progression.

Décisions de cadrage (12/07/2026) — R4 découpé :
- **R4a (cette US)** = historique + stats distance/temps + courbe d'allure **globale**. Sur données
  existantes, **sans nouveau build**.
- **R4b (ultérieur)** = records d'allure (segment glissant) + maj auto de l'allure de référence (5.30/5.31).
- **Export GPX (5.33)** = incrément dédié (nécessite `expo-sharing` + `expo-file-system` → nouveau build).
- **Dénivelé (5.32)** = **différé** : aucune altitude n'est captée aujourd'hui (`GpsPoint = { lat, lng, t }`) ;
  nécessiterait de modifier le tracker (R1) + étendre `GpsPoint`/le codec + un nouveau build.
- **Découpages « par type de séance »** (5.28 nombre par type, 5.29 courbe par type) = **différés** : les
  courses (`runs`) sont toutes des **courses libres** sans `session_type` (le lien tracker↔séance planifiée
  a été différé en R3c-i). Les stats et la courbe sont donc **globales** au MVP.

## 2. Comportement attendu

1. **Ouvrir l'historique** (onglet Course → « Historique ») : l'écran affiche les 3 sections.
2. **Statistiques** : le sélecteur **Semaine / Mois / Depuis le début** recalcule distance totale, temps
   total et nombre de courses sur la période. Semaine = **lundi→dimanche** courante ; Mois = mois calendaire
   courant ; Depuis le début = toutes les courses. Distances/temps formatés via `useUnits`.
3. **Courbe d'allure** : un point par course (allure moyenne) sur la fenêtre choisie (**30** ou **90** jours
   glissants jusqu'à aujourd'hui) ; axe en allure formatée (`useUnits.formatPace`). Une **tendance** est
   affichée (comparaison de l'allure moyenne du début vs la fin de la fenêtre : « en progrès » si l'allure
   diminue, « en baisse » si elle augmente, « stable » sinon ; seuil de stabilité à fixer, ex. ±2 %).
4. **Liste** : courses terminées triées par `finished_at` décroissant (requête `useRunHistory` existante) ; chaque ligne montre
   date (JJ/MM/AAAA), distance, allure moyenne, durée ; **tap → `run/summary?id=<runId>`**.
5. **Réactif** (`useQuery`) ; **offline-first** (lecture locale, aucune dépendance réseau).

## 3. Règles métier

- **Périodes de stats** : calendaires. « Semaine » = du lundi 00:00 local au dimanche ; « Mois » = 1er du
  mois au dernier jour ; « Depuis le début » = toutes les courses terminées. Comparaison de dates via clé
  calendaire locale `AAAA-MM-JJ` (réutilise `localDayKey`/helpers de `date.ts`), **sans dérive fuseau/DST**.
- **Fenêtres de courbe** : **glissantes** (30 / 90 derniers jours jusqu'à aujourd'hui) — distinct des périodes
  de stats (calendaires). Une course entre dans la courbe si elle a une **allure moyenne** (`avg_pace_s_per_km`
  non nul).
- **Courses manuelles** (`source = 'manual'`, sans GPS) : **comptent** dans les stats distance/temps **si une
  distance est renseignée** (distance saisie a posteriori) et dans le nombre de courses ; elles n'entrent dans
  la **courbe d'allure** que si une allure moyenne existe. (Cohérent avec running.md §8 : le manuel compte pour
  historique/durée ; exclu des **records** — hors périmètre R4a.)
- **Courses non terminées** (en cours / statut ≠ terminé) : **exclues** de l'historique, des stats et de la
  courbe (seules les courses `finished_at` non nul comptent).
- **Allure** : plus l'allure (s/km) est **basse**, plus c'est **rapide** — la « tendance en progrès » = allure
  qui **diminue**. À refléter dans le libellé et l'éventuelle couleur.

## 4. Architecture

- **`@wellness/shared`** (TDD, pur) — nouveau `run-stats.ts` :
  - `aggregateRunStats(runs, period, todayKey)` → `{ totalDistanceM, totalDurationS, count }` pour
    `period ∈ 'week' | 'month' | 'all'`. `runs` = forme minimale `{ finishedAtDayKey, distanceM, durationS }`
    (le repo fournit la clé de jour locale ; la fonction ne fait que filtrer/sommer).
  - `paceTrendPoints(runs, days, todayKey)` → points `{ dayKey, paceSPerKm }` des courses des `days` derniers
    jours ayant une allure, triés chronologiquement.
  - `paceTrend(points)` → `'improving' | 'declining' | 'stable'` (compare moyenne 1ère moitié vs 2ᵉ moitié,
    seuil ±2 %). Purs, testés (périodes, fenêtres, tendance, cas manuel/sans allure, dates calendaires).
  - Réutilise `localDayKey`/`startOfWeek`/`addDays` de `date.ts`.
- **Repository** (`run-repository.ts`) — hooks de lecture réactifs (aucune écriture) :
  - Réutiliser `useRunHistory()` (liste) — sa requête filtre déjà `status='completed' ORDER BY finished_at DESC`.
    ⚠️ **Non-régression** : `useRunHistory` a des consommateurs existants (dashboard streak / jour d'entraînement) ;
    si une extension est nécessaire, elle doit rester **rétrocompatible** (ne pas casser les champs consommés)
    ou passer par une **nouvelle requête** dédiée. Ne pas régresser le streak.
  - `useRunStats(period)` → agrège via `aggregateRunStats` sur les courses terminées de l'utilisateur.
  - `usePaceTrend(days)` → `{ points, trend }` via `paceTrendPoints` + `paceTrend`.
  - Les hooks calculent `todayKey`/bornes en JS local et passent des paramètres liés aux requêtes ; le
    filtrage fin (période/fenêtre) peut se faire en SQL (bornes de date) **ou** en TS via les helpers shared —
    à trancher au plan (préférence : bornes larges en SQL, agrégation fine en shared testé).
- **Écran** `apps/mobile/src/app/running-history/index.tsx` (+ `_layout.tsx`) — 3 sections :
  en-tête stats + `Segment` période ; `ProgressLineChart` (existant) pour la courbe + `Segment` 30/90 j +
  libellé tendance ; liste (FlatList/scroll) des courses → `router.push('run/summary?id=' + id)`. `EmptyState`
  si aucune course. Réutilise `useUnits`, `Screen`, `Card`, `ScreenHeader`, `Segment`, `EmptyState`.
- **Entrée** : bouton **« Historique »** dans l'onglet Course (`(tabs)/running.tsx`), conditionné à
  `activePillars.includes('running')`, à côté de « Mon planning » / « Mes programmes de course ».
- **i18n** FR+EN : `running.history.{ title, empty, statsTitle, period, week, month, all, totalDistance,
  totalTime, runCount, paceTitle, days30, days90, trend, trendImproving, trendDeclining, trendStable }`
  (+ réutilise formats existants). Parité, aucune chaîne/unité en dur.
- **Graphes** : réutilise `react-native-gifted-charts` via `ProgressLineChart` (déjà présent) — **aucune
  nouvelle dépendance**.
