# US 1.2 — Connexion via Google (OAuth)

> Permettre de **créer un compte / se connecter avec Google**, en complément de l'e-mail/mot de passe.
> Sign-In **natif** Android (`@react-native-google-signin/google-signin`) → `supabase.auth.signInWithIdToken`.
> Roadmap [1.2](../../../roadmap/roadmap.md) (V0.8, conservé — arbitrage E ; **OAuth Apple reporté** avec iOS).
> Branche : `feature/1.2-oauth-google` · Date : 24/07/2026 ·
> **Statut : à valider (pas de code avant validation Florian/Damien).**
> **Aucune migration.** ⚠️ **Module natif ajouté → nouveau dev build.** Prérequis externes (Google Cloud +
> Supabase Auth) = **déploiement contrôlé**, ne bloquent pas le cadrage.

## 0. Contexte

`sign-in.tsx` / `sign-up.tsx` ne proposent que l'e-mail/mot de passe (`supabase.auth.signInWithPassword` /
`signUp`). La session est gérée par `auth-store` via `supabase.auth.onAuthStateChange` (persistance + refresh
silencieux). L'inscription e-mail impose déjà, **côté client** (gardes non persistées) : **âge 16+**
(`MIN_SIGNUP_AGE`, `isAtLeast`) + **case CGU/confidentialité**. OAuth Google est **conservé** au lancement
(arbitrage E) ; **OAuth Apple** ne l'est pas (reporté avec iOS).

Décisions de cadrage (brainstorming Florian, 24/07/2026) :
- **Approche = Sign-In natif** (`@react-native-google-signin/google-signin`) → récupération de l'`idToken` →
  `supabase.auth.signInWithIdToken({ provider: 'google', token })`. UX Android de référence (sélecteur de
  compte in-app), pas de flux navigateur/deep-link. Module natif → **dev build**.
- **Liaison de compte = automatique par e-mail vérifié** (Supabase) : même e-mail = même compte. L'e-mail
  Google étant vérifié par Google, la liaison est sûre.
- **Consentement = garde par l'action** (option A) : une **mention** sous le bouton (CGU + confidentialité +
  16+), l'acceptation résultant de l'action de connexion. Cohérent avec le modèle actuel (consentement **non
  persisté**). La persistance serveur du consentement = **US transverse dédiée** (hors périmètre).
- **Placement = les deux écrans** (connexion + inscription), même mention.

## 1. Périmètre à livrer

- **Dépendance** `@react-native-google-signin/google-signin` + configuration `GoogleSignin.configure({ webClientId })`
  au démarrage (une fois).
- **Constante/env** `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` (placeholder tant que non fourni) + entrée
  correspondante dans **`apps/mobile/.env.example`** (`EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID=`), comme les autres clés.
- **Action `signInWithGoogle()`** dans `auth-store` : `hasPlayServices` → `GoogleSignin.signIn()` → `idToken` →
  `supabase.auth.signInWithIdToken`. Annulation = no-op ; erreurs mappées en message i18n.
- **Bouton « Continuer avec Google »** (logo + libellé, guidelines Google) sur `sign-in.tsx` et `sign-up.tsx`,
  séparateur « ou », + **mention de consentement** (liens CGU/confidentialité).
- **Helper pur** de mapping d'erreurs Google → clé i18n (**testé**).
- **i18n FR/EN** (bouton, mention, erreurs). Aucune chaîne en dur.

**Hors périmètre (à ne pas implémenter ici) :**
- **OAuth Apple** (iOS — reporté, [ADR-004](../../../adr/ADR-004-plateforme-lancement.md)).
- **Persistance serveur du consentement / de l'âge** (US transverse — cf. §0).
- **Délier un compte Google** / écran de gestion multi-providers dans les Réglages.
- **Google One Tap / auto-login** silencieux au lancement.
- **Configuration Google Cloud / Supabase Auth** = étapes de **déploiement contrôlé** (§6), pas du code.

## 2. Comportement attendu

### 2.1 Configuration au démarrage
- `GoogleSignin.configure({ webClientId: EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID })` appelé une fois à l'init de l'app
  (avant tout usage). Si le Web Client ID est absent (placeholder), le bouton peut rester visible mais l'action
  échoue proprement (message d'erreur) — état transitoire avant la mise en place des clés.

### 2.2 Parcours nominal
- Tap **« Continuer avec Google »** → `hasPlayServices()` → sélecteur de compte Google natif → au choix d'un
  compte, on récupère l'`idToken` → `supabase.auth.signInWithIdToken({ provider: 'google', token })`.
- Succès → `onAuthStateChange` met à jour la session → le layout racine redirige (**même chemin que
  l'e-mail/mot de passe**). Un **nouveau** compte (sans profil) tombe sur la **gate d'onboarding existante** ;
  un compte lié existant entre directement dans l'app.

### 2.3 Consentement (mention par action)
- Sous le bouton, sur les deux écrans : « En continuant avec Google, tu acceptes les [CGU] et la [politique de
  confidentialité] et confirmes avoir 16 ans ou plus. » (liens vers `terms`/`privacy`). L'acceptation résulte de
  l'action ; aucune case à cocher (option A).

### 2.4 Liaison de compte
- **Même e-mail vérifié** → Supabase rattache l'identité Google au compte existant (un seul compte).
- **Compte e-mail existant non vérifié** (cas limite) → Supabase refuse la liaison → message clair (« vérifie
  d'abord ton e-mail avant de lier Google »).

### 2.5 Erreurs & annulation
- **Annulation** (`SIGN_IN_CANCELLED`) → **no-op** (retour à l'écran, aucun message d'erreur).
- **Play Services indisponible / obsolète** → message dédié.
- **Hors-ligne** → message « connexion internet requise » (l'auth initiale exige le réseau, contrairement au
  reste de l'app).
- **Échec d'échange Supabase** (token invalide, liaison refusée…) → message générique + log `console.warn`.

## 3. Architecture

- **`apps/mobile/src/lib/google-auth-errors.ts`** (ou dans `auth-store`) : `mapGoogleSignInError(err): string`
  (clé i18n) — **pur, testé**. Doit couvrir **les deux origines** d'erreur : (a) les `statusCodes` de la lib
  Google (`PLAY_SERVICES_NOT_AVAILABLE`, etc. ; `SIGN_IN_CANCELLED` traité en amont, pas ici) **et** (b) les
  erreurs remontées par `signInWithIdToken` (échec réseau/fetch Supabase, liaison refusée e-mail non vérifié).
  Les tests couvrent les deux familles.
- **`auth-store.ts`** : `signInWithGoogle(): Promise<AuthResult>` (I/O : SDK Google + Supabase). Réutilise le
  type `AuthResult` existant. `SIGN_IN_CANCELLED` → `{ error: null }` (no-op).
- **`apps/mobile/src/lib/google-signin.ts`** (ou init existant) : `configureGoogleSignin()` lit
  `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`, **appelé une fois au démarrage depuis `apps/mobile/src/app/_layout.tsx`**
  (à côté des `useEffect` d'init existants, ou import à effet de bord — à trancher au plan).
- **`components/GoogleButton.tsx`** (ou bouton dédié) : bouton conforme guidelines Google, réutilisé par les
  deux écrans (DRY).
- **`sign-in.tsx` / `sign-up.tsx`** : séparateur « ou » + `GoogleButton` + mention consentement.
- **Config native** : `app.json` (plugin de la lib si requis) + dépendance ; build EAS dev.

## 4. i18n (FR + EN)

Clés indicatives : `auth.google.{button, consent.prefix, consent.terms, consent.middle, consent.privacy,
consent.suffix, orSeparator}` ; `auth.google.errors.{playServices, offline, linkUnverified, generic}`. Parité
stricte. **Clés dédiées `auth.google.consent.*` nécessaires** (à ne PAS réutiliser `auth.signUp.consent.*` : la
formulation existante n'inclut ni « 16 ans ou plus » ni le cadrage « En continuant avec Google… »). Exemples
FR→EN : « Continuer avec Google » → « Continue with Google » ; « Connexion internet requise » → « Internet
connection required ».

## 5. Sécurité & RGPD

- L'`idToken` Google est vérifié côté Supabase (audience = Web Client ID) ; aucun secret client dans l'app.
- Liaison sur **e-mail vérifié** uniquement (pas d'usurpation via e-mail non vérifié).
- Consentement présenté **avant** l'action (mention) ; CGU + confidentialité + 16+.
- Aucune donnée supplémentaire demandée à Google au-delà de l'identité de base (email, profil).

## 6. Déploiement (contrôlé — hors code)

1. **Google Cloud Console** : Client ID **Web** + Client ID **Android** (package name + **SHA-1 du build EAS**).
2. **Supabase Auth** : activer le provider Google (Client ID/secret **Web**) ; vérifier la liaison par e-mail.
3. **`EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`** renseignée (env / `.env`).
4. **Nouveau dev build EAS** (module natif) pour la recette.

## 7. Cas limites

- **Annulation** utilisateur → aucun effet, aucun message.
- **Play Services absents** (émulateur sans Google) → message dédié ; recette possible sur device réel.
- **E-mail existant non vérifié** → liaison refusée, message.
- **Web Client ID non configuré** (avant déploiement) → l'action échoue proprement (message), pas de crash.
- **Hors-ligne** → message réseau.
- **Compte Google déjà lié** → connexion directe (pas de doublon).

## 9. Critères d'acceptation (recette)

1. **Nouveau compte Google** : « Continuer avec Google » → sélecteur → choix d'un compte **sans compte
   existant** → session ouverte → **onboarding** s'affiche (nouveau compte).
2. **Reconnexion Google** : se déconnecter, re-« Continuer avec Google » → retour direct dans l'app (compte lié).
3. **Liaison e-mail** : sur un compte créé en e-mail/mot de passe (**e-mail vérifié**), se connecter avec Google
   sur la **même adresse** → **même compte** (données retrouvées), pas de doublon.
4. **Consentement** : la mention (CGU + confidentialité + 16+) est visible sous le bouton, liens fonctionnels,
   sur les deux écrans.
5. **Annulation** : fermer le sélecteur → retour à l'écran, **aucune erreur**.
6. **Hors-ligne** : en mode avion, le bouton affiche un message « connexion requise » (pas de crash).
7. **i18n** : bouton + mention + messages d'erreur traduits en anglais.
