# US 1.22 — Aide & support (FAQ + contact + signalement de bug)

> Donner à l'utilisateur un point d'entrée **« Aide & support »** dans les Réglages : une **FAQ**
> embarquée (bilingue, hors-ligne) et deux actions de contact — **« Nous contacter »** et
> **« Signaler un bug »** — qui ouvrent le **client mail natif** avec un message pré-rempli.
> Prérequis avant d'ouvrir la bêta (canal de retour testeurs). Roadmap
> [1.22](../../../roadmap/roadmap.md) (V0.8). Branche : `feature/1.22-aide-support` · Date : 24/07/2026 ·
> **Statut : à valider (pas de code avant validation Florian/Damien).**
> **Aucune migration, aucun serveur** (FAQ embarquée + mail natif).

## 0. Contexte

Les Réglages n'offrent aujourd'hui **aucun canal d'aide ni de contact**. Avant d'ouvrir l'app à de vrais
testeurs (bêta Play interne, V0.8), il faut au minimum : répondre aux questions courantes (FAQ) et permettre
de **remonter un bug ou une question**. C'est un item du **périmètre de lancement** (V0.8).

Décisions de cadrage (brainstorming Florian, 24/07/2026) :
- **Canal de contact = client mail natif** (option A). Le formulaire ouvre le mail de l'utilisateur pré-rempli
  vers une adresse de support ; l'utilisateur envoie depuis **sa** boîte. **Zéro backend, zéro migration, zéro
  coût**, offline-compatible, et l'utilisateur garde une trace de son envoi. (Une file de tickets dans le
  back-office admin reste une évolution ultérieure si le volume le justifie.)
- **FAQ = statique embarquée** (option A) dans les fichiers i18n FR/EN. Petite FAQ (≈ 7 entrées) suffisante au
  lancement ; 100 % hors-ligne. (Une FAQ éditable à chaud via l'admin reste une évolution ultérieure.)
- **Deux entrées distinctes** : « Nous contacter » (mail simple, aucune métadonnée) et « Signaler un bug »
  (mail + **bloc technique minimal** pré-rempli).
- **Métadonnées du signalement = minimales** (option A) : version app + build, OS + version, modèle
  d'appareil, langue. **Aucune donnée personnelle** (pas d'UUID, pas de logs). Bloc **visible et effaçable**
  par l'utilisateur dans le corps du mail (cohérent RGPD).
- **Adresse de destination** : **placeholder** (`SUPPORT_EMAIL`, constante centralisée) — à trancher par
  Florian avant le build (création d'une boîte de support dédiée).

Contexte technique (à confirmer au moment du code contre les docs Expo SDK 57) :
- Mail natif via **`expo-mail-composer`** (`MailComposer.composeAsync`, `isAvailableAsync`).
- Métadonnées via **`expo-application`** (version/build), **`expo-device`** (modèle, OS, version OS),
  `Platform`, et la langue courante de l'app. Modules à installer via `npx expo install`.
- Insertion dans [settings.tsx](../../../../apps/mobile/src/app/settings.tsx) sur le même patron que les autres
  sections (bouton → `router.push` vers un sous-écran, comme `/account-delete`).

## 1. Périmètre à livrer

- **Section « Aide & support »** dans les Réglages : un bouton menant au sous-écran `/help`.
- **Écran `/help`** :
  - **FAQ** : liste de questions/réponses **repliables** (tap pour déplier), contenu embarqué i18n FR/EN.
  - **Contact** : deux actions — **« Nous contacter »** et **« Signaler un bug »**.
- **Helper pur** `formatBugReportBody(meta, t)` (gabarit de message + bloc technique) — **testé** (déterministe).
- **Collecte des métadonnées** `collectSupportMeta()` (I/O natif, non pure), fournie au helper.
- **Constante** `SUPPORT_EMAIL` centralisée (placeholder).
- **i18n** FR/EN complète (FAQ + libellés + objets/gabarits de mail).

**Hors périmètre (à ne pas implémenter ici) :**
- **Table Supabase** / file de tickets côté admin (option B du cadrage) — évolution ultérieure.
- **FAQ éditable à chaud** via le back-office (option B) — évolution ultérieure.
- **Service tiers** (Formspree, support desk) — écarté.
- **UUID, logs, captures d'écran** joints au bug — écartés (métadonnées minimales seulement).
- **Chat / support en direct**, base de connaissances en ligne.

## 2. Comportement attendu

### 2.1 Accès
- Réglages → section **« Aide & support »** → bouton **« Aide & support »** → `router.push('/help')`.
  Placement cohérent (ex. au-dessus de la section Données/Zone de danger). Accessible **hors-ligne**.

### 2.2 FAQ
- Liste de ≈ 7 entrées **repliables** en **accordéon mono-ouverture** : ouvrir une question referme la
  précédente (état = un seul index actif, `null` = tout replié). Chaque entrée = une question (titre pressable,
  rôle bouton + `accessibilityState.expanded`) et une réponse dépliée.
- Contenu embarqué (i18n, `returnObjects`), **bilingue FR/EN**. Ensemble initial proposé :
  1. **Mode hors-ligne** — « L'app fonctionne sans connexion ; tes données sont enregistrées sur l'appareil et
     se synchronisent automatiquement dès qu'une connexion est disponible. »
  2. **Synchro multi-appareils** — « Connecte-toi avec le même compte : tes données se synchronisent entre tes
     appareils en arrière-plan. »
  3. **Activer/désactiver un pilier** — « Réglages → Piliers actifs. Les onglets des piliers désactivés sont
     masqués et réapparaissent quand tu les réactives. »
  4. **Changer les unités / la langue** — « Réglages → Unités (métrique/impérial) et Langue (français/anglais). »
  5. **Exporter mes données** — « Réglages → Exporter mes données : tu récupères une copie de toutes tes
     données au format JSON. » *(renvoi CONF-01)*
  6. **Supprimer mon compte** — « Réglages → Zone de danger → Supprimer mon compte. Un délai de grâce de 30
     jours permet de revenir en arrière. » *(renvoi CONF-02)*
  7. **L'app est-elle gratuite ?** — « Oui, l'application est entièrement gratuite. »
  > La teneur exacte des réponses est ajustable à la rédaction ; les renvois CONF-01/CONF-02 restent purement
  > **textuels** (pas de navigation croisée depuis la FAQ).

### 2.3 Nous contacter
- Bouton **« Nous contacter »** → `MailComposer.composeAsync` :
  - destinataire = `SUPPORT_EMAIL` ;
  - objet pré-rempli depuis l'i18n (`help.contact.subject`, ex. « [Wellness] Question / contact ») ;
  - corps **vide** (aucune métadonnée).
- L'utilisateur rédige et envoie depuis son client mail. Annulation = sans effet.

### 2.4 Signaler un bug
- Bouton **« Signaler un bug »** → `MailComposer.composeAsync` :
  - destinataire = `SUPPORT_EMAIL` ;
  - objet pré-rempli depuis l'i18n (`help.bug.subject`, ex. « [Wellness] Signalement de bug ») ;
  - corps = **gabarit** (`formatBugReportBody`) : une invite (« Décris le problème rencontré : … ») **suivie**
    d'un bloc technique délimité, ex. :
    ```
    ——— Informations techniques (à conserver) ———
    App : 1.0.0 (build 42)
    Système : Android 14
    Appareil : Pixel 7
    Langue : fr
    ```
- Le bloc est **visible et effaçable** par l'utilisateur (cohérent RGPD : il voit ce qu'il envoie).

### 2.5 Indisponibilité du client mail
- Avant d'ouvrir : `MailComposer.isAvailableAsync()`. Si **false** (aucun client mail configuré / non
  supporté) → **`Alert`** affichant l'adresse `SUPPORT_EMAIL` (« Aucune application mail configurée. Écris-nous
  à : … ») pour que l'utilisateur puisse la recopier. **Pas de crash, pas d'écran mort.**

## 3. Architecture

- **`apps/mobile/src/lib/support.ts`** :
  - `SUPPORT_EMAIL` — constante centralisée (placeholder, à changer avant le build).
  - `collectSupportMeta(): SupportMeta` — lit version/build (`expo-application`), modèle & OS
    (`expo-device`/`Platform`), langue (i18n). **Protégée** (jamais bloquante ; valeurs manquantes → « — »).
  - `formatBugReportBody(meta, t): string` — **pur**, assemble invite + bloc technique traduit. **Testé**
    (Jest mobile) : bloc déterministe pour un `meta` donné, présence des 4 champs, libellés via `t`.
  - `contactSupport(kind: 'contact' | 'bug', t)` — orchestration : construit objet/corps, `isAvailableAsync`,
    `composeAsync`, fallback `Alert`. **Renvoie un résultat typé** `{ ok: true } | { fallback: true }` (permet un
    test d'orchestration du chemin fallback, en plus du helper pur).
- **`apps/mobile/src/app/help.tsx`** — écran : FAQ repliable (composant local `FaqItem`) + deux boutons
  d'action. Aucune logique métier lourde ; délègue à `support.ts`.
- **Réglages** ([settings.tsx](../../../../apps/mobile/src/app/settings.tsx)) : nouvelle section + bouton
  `router.push('/help')`.

> Le découpage isole la partie **pure et testable** (`formatBugReportBody`) de l'**I/O natif**
> (`collectSupportMeta`, `composeAsync`), conformément aux bonnes pratiques offline/testabilité du projet.

## 4. i18n (FR + EN)

Aucune chaîne en dur ; parité stricte FR/EN. Clés indicatives :
- `settings.help.{title, button}` (section Réglages).
- `help.{title}`, `help.faq.items` (**liste** `[{ q, a }]` via `returnObjects`), `help.contact.{title,
  intro}`, `help.contact.{contactButton, bugButton}`.
- `help.bug.{subject, prompt, techHeader, appLabel, systemLabel, deviceLabel, languageLabel}`.
- `help.contact.{subject}`, `help.mailUnavailableTitle`, `help.mailUnavailableBody`.

Exemples FR→EN : « Aide & support » → « Help & support » ; « Nous contacter » → « Contact us » ; « Signaler un
bug » → « Report a bug » ; « Informations techniques (à conserver) » → « Technical information (please keep) ».

## 5. Offline & performance

- **100 % hors-ligne** : la FAQ est embarquée ; le mail est composé localement et part quand le client mail se
  synchronise. Aucun appel réseau, aucune migration.
- Coût négligeable (rendu d'une liste statique + ouverture d'un composeur natif).

## 6. Sécurité & RGPD

- **Aucune donnée personnelle transmise à notre insu** : le mail part depuis la boîte de l'utilisateur, il voit
  et peut modifier tout le contenu (y compris le bloc technique) avant l'envoi.
- Métadonnées **minimales et non identifiantes** (version, OS, modèle, langue) — **pas d'UUID, pas de logs**.
- Aucune écriture serveur, aucune collecte silencieuse.

## 7. Cas limites

- **Client mail indisponible** (`isAvailableAsync` false) → `Alert` avec l'adresse (§2.5).
- **Composeur annulé** par l'utilisateur → sans effet, retour à l'écran d'aide.
- **Métadonnée manquante** (modèle/OS non résolus) → champ « — », jamais de crash.
- **Hors-ligne** → FAQ et ouverture du composeur fonctionnent (envoi différé côté client mail).
- **Langue** : basculer FR/EN met à jour FAQ, libellés et gabarit du mail.

## 8. Definition of Done

- `support.ts` : `SUPPORT_EMAIL` (placeholder), `collectSupportMeta`, `formatBugReportBody` (**pur, testé**),
  `contactSupport` (mail natif + fallback).
- Écran `/help` : FAQ repliable bilingue + « Nous contacter » + « Signaler un bug ».
- Section « Aide & support » dans les Réglages (bouton → `/help`).
- i18n FR/EN complète (parité), aucune chaîne en dur.
- `typecheck` + `lint` + tests (helper pur + smoke écran) verts.
- Maquette (`design/1.22-aide-support/`) validée Florian/Damien **avant** le code.

## 9. Critères d'acceptation (recette)

1. **Accès** : Réglages → « Aide & support » → l'écran `/help` s'ouvre (y compris **hors-ligne**).
2. **FAQ** : les ≈ 7 entrées s'affichent ; taper une question la déplie/replie ; réponses cohérentes.
3. **Nous contacter** : le bouton ouvre le client mail avec destinataire = adresse de support, objet
   pré-rempli, **corps vide**.
4. **Signaler un bug** : le bouton ouvre le client mail avec l'objet bug + un corps contenant l'invite **et**
   le bloc technique (app, système, appareil, langue) correctement renseigné.
5. **Bloc effaçable** : le bloc technique est éditable/supprimable dans le mail avant envoi.
6. **Mail indisponible** : sans client mail configuré, une `Alert` affiche l'adresse de support (pas de crash).
7. **i18n** : tout le parcours (FAQ, boutons, objet/gabarit du mail, alerte) traduit en anglais.
