# US 8.8a — Consultation des utilisateurs (back-office)

_Spec fonctionnelle. Statut : en validation (brainstorming Florian, 16/07/2026). Branche :
`feature/8.8a-admin-consultation-utilisateurs` (depuis `dev`). Première moitié de l'US 8.8 (roadmap
V0.7) ; le **bannissement** est traité séparément en **8.8b**._

## 1. Contexte & objectif

La roadmap 8.8 prévoit une **gestion des utilisateurs** dans le back-office : liste des comptes,
recherche, profil en lecture seule, bannir/débannir. On **découpe** (décision Florian, 16/07/2026) :

- **8.8a (cette US)** — **consultation** : lister les comptes, rechercher par email, consulter une
  fiche profil en lecture seule. **Lecture pure, aucun risque d'écriture.**
- **8.8b (ultérieure)** — **bannissement** : RPC `SECURITY DEFINER` sur `auth.users.banned_until` +
  table `user_bans` (motif) + actions bannir/débannir. Sensible (écrit dans le schéma `auth`) → cadré
  et relu **avec Damien**.

**Contrainte structurante** : l'admin (`apps/admin`) n'utilise que la **clé anon** (jamais
`service_role` — cf. [supabase.ts](../../../apps/admin/src/lib/supabase.ts)). Or l'email, la date
d'inscription et la dernière connexion vivent dans **`auth.users`**, **illisible en anon**. L'accès se
fait donc par une **vue SQL protégée**, exécutée avec les droits de son propriétaire.

Objectif : donner aux rôles **`super_admin`** et **`moderator`** une vue consolidée et **sobre** des
comptes, sans exposer de données de santé ni le schéma `auth` au client.

## 3. Modèle de données (lecture seule)

### 3.1 Fonction `public.can_manage_users()`
Sur le modèle de `is_admin()`/`is_super_admin()`
([20260713100000_admin_user_roles.sql](../../../supabase/migrations/20260713100000_admin_user_roles.sql)) :
`SECURITY DEFINER`, `STABLE`, `search_path = public`. Renvoie `true` s'il existe une attribution
active (`deleted_at IS NULL`) de rôle `super_admin` **ou** `moderator` pour `auth.uid()`.

### 3.2 Vue `public.admin_users`
- Créée par le rôle de migration (**propriétaire privilégié = `postgres`**) et **`security_invoker =
  false`** (défaut) → la vue lit `auth.users` **et contourne la RLS** de `profiles`/`user_settings`
  avec les droits du propriétaire. C'est **l'effet recherché** (voir tous les comptes) — mais cela
  signifie que **la seule barrière serveur est le `WHERE public.can_manage_users()`** (à souligner
  pour la relecture Damien).
- **`WHERE public.can_manage_users()`** intégré → un utilisateur non habilité (compte normal ou
  `content_editor`, ou anon dont `auth.uid()` est NULL) obtient **0 ligne**. **Barrière serveur
  authoritative** (ne repose pas sur le client).
- `security_barrier = true` : gardé par prudence, mais bénéfice **marginal** ici (le `WHERE` est un
  gate **tout-ou-rien**, il ne référence aucune colonne de ligne) — ce n'est pas la clé de voûte, qui
  reste `security_invoker=false` + le `WHERE`.
- **Privilèges explicites** : `GRANT SELECT ON public.admin_users TO authenticated;` (l'admin est
  toujours connecté) **et** `REVOKE ALL ON public.admin_users FROM anon;` — sur Supabase les *default
  privileges* accordent souvent SELECT à `anon` automatiquement sur les nouveaux objets `public` ; le
  `REVOKE` explicite ferme la porte (la protection tiendrait de toute façon via `can_manage_users()`,
  mais défense en profondeur).
- **Colonnes exposées (strictement limitées, jamais de secret)** :

| Colonne | Source | Note |
|---|---|---|
| `id` | `auth.users.id` | identifiant du compte |
| `email` | `auth.users.email` | recherche par email (`ilike`) |
| `created_at` | `auth.users.created_at` | date d'inscription |
| `last_sign_in_at` | `auth.users.last_sign_in_at` | « dernière activité » (proxy) |
| `is_banned` | calculé | `banned_until IS NOT NULL AND banned_until > now()` |
| `first_name` | `profiles.first_name` | LEFT JOIN (peut être `null`) |
| `main_goal` | `profiles.main_goal` | LEFT JOIN |
| `onboarding_completed_at` | `profiles.onboarding_completed_at` | LEFT JOIN |
| `active_pillars` | `user_settings.active_pillars` | LEFT JOIN (jsonb) |
| `language` | `user_settings.language` | LEFT JOIN |

- **Jointures en `LEFT JOIN`** sur `profiles`/`user_settings` : un compte sans profil (onboarding non
  terminé) ou sans réglages **apparaît quand même**, colonnes profil à `null`.
- **Exclusion des soft-deleted** : ne pas lister les `profiles.deleted_at`/`user_settings.deleted_at`
  n'a pas de sens (le compte auth reste) — on liste **par `auth.users`** ; les jointures ignorent les
  lignes profil/settings soft-deleted (`deleted_at IS NULL` dans la condition de jointure) mais le
  compte reste listé.
- **Aucune écriture** : la vue est en lecture seule (pas de règles INSERT/UPDATE).

> ⚠️ **Checkpoint migration 🔴** (workflow CLAUDE.md, dev sur cloud sans Docker) : `db:new` → écrire
> le SQL → `db:push:dry` → `db:push` → `db:types` → cocher dans
> [MIGRATIONS.md](../../../supabase/MIGRATIONS.md). **Pas de sync rule** (table admin/web, hors
> PowerSync). La vue lit `auth.users` : vérifier après apply que `SELECT` fonctionne pour un
> `super_admin`/`moderator` et renvoie **0 ligne** pour un compte normal.
>
> ⚠️ **Cache PostgREST** : une nouvelle vue `public` n'est requêtable via l'API qu'après rechargement
> du schéma (généralement auto après DDL sur le cloud). Si `.from('admin_users')` renvoie « relation
> inconnue », déclencher `NOTIFY pgrst, 'reload schema';`.
>
> ⚠️ **Ordre de build** : la couche data `users.ts` type `AdminUserRow` sur
> `Database['public']['Views']['admin_users']['Row']`. L'espace `Views` existe déjà dans
> [database.types.ts](../../../packages/shared/src/database.types.ts) (vide pour l'instant) → il sera
> peuplé par `db:types` **après** apply. Ne pas écrire/committer `users.ts` **avant** `db:types`,
> sinon `typecheck` casse.

## 4. Écrans (apps/admin, FR)

### 4.1 Liste `/users`
- Tableau paginé : **Email · Inscrit le · Dernière connexion · Piliers actifs · Statut**.
- **Recherche par email** (champ texte → `ilike %saisie%`, insensible à la casse).
- **Statut** : badge « Actif » / « Banni » (lecture ; `is_banned`).
- **Piliers actifs** : rendu compact (ex. « Muscu · Course · Nutrition » à partir de `active_pillars`).
- **Pagination** (taille de page fixe, ex. 25 ; `range`/`limit-offset` PostgREST). Tri par défaut :
  inscription décroissante.
- Ligne cliquable → fiche `/users/:id`.
- **États** : chargement, vide (aucun compte / aucun résultat de recherche), erreur.

### 4.2 Fiche `/users/:id` (lecture seule, sobre)
- **Compte** : email, date d'inscription, dernière connexion, statut (Actif/Banni).
- **Configuration** : piliers actifs, langue.
- **Profil** : prénom (si renseigné), objectif principal (`main_goal`), onboarding terminé (oui/non
  via `onboarding_completed_at`).
- **PAS de données de santé** (poids, taille, sexe, date de naissance) — minimisation RGPD.
- **Aucun bouton d'action** (le bannissement = 8.8b). Éventuel emplacement réservé, non actif.

### 4.3 Navigation & gate
- **Créer la capacité `canManageUsers`** (= `super_admin` OU `moderator`) dans le contexte de rôles
  (`rolesContext.ts` + `RolesProvider.tsx`) et un garde de route **`RequireCanManageUsers`** (`App.tsx`),
  calqués sur `RequireSuperAdmin`/`RequireContentEditor`. **Ne pas** réutiliser `isAdmin`/`isContentEditor`.
- **Convertir l'entrée de nav** « Utilisateurs » : la retirer de `NAV_SOON` (placeholder grisé
  actuel) et ajouter un `NavLink to="/users"` conditionné par `canManageUsers` (comme les liens
  `isContentEditor`/`isSuperAdmin` existants).
- Un `content_editor` ne voit ni l'entrée ni les données : **double barrière** — gate client
  (`RequireCanManageUsers`) **et** `WHERE can_manage_users()` dans la vue (authoritative serveur).

## 5. Couche data — `apps/admin/src/data/users.ts`

- `listUsers({ search?, page?, pageSize? })` → `{ rows: AdminUserRow[]; count: number; error }`
  (`.from('admin_users').select('*', { count: 'exact' }).ilike('email', …).order('created_at',
  { ascending: false }).range(…)`).
- `getUser(id)` → `{ user: AdminUserRow | null; error }` (`.eq('id', id).maybeSingle()`).
- Type `AdminUserRow` dérivé de `Database['public']['Views']['admin_users']['Row']` après `db:types`.
- **Pas de `logAudit`** : la consultation est une lecture (l'audit 8.10 trace les écritures ; lister
  n'écrit rien). _(Le ban en 8.8b, lui, sera audité.)_

## 7. Cas limites

- **Compte sans profil** (onboarding non terminé) → listé, prénom/objectif `null` → afficher « — ».
- **Compte sans réglages** → piliers/langue `null` → défaut d'affichage neutre.
- **Recherche vide** → liste complète paginée ; **aucun résultat** → état vide dédié.
- **`content_editor` ou compte normal** qui forcerait la requête → vue renvoie **0 ligne** (protégée
  serveur), et l'entrée de nav est masquée.
- **`last_sign_in_at` null** (compte jamais connecté depuis créa) → afficher « jamais » / « — ».
- **`banned_until` passé** → `is_banned = false` (le ban expiré ne compte pas).
- **Volume** : MVP early (peu de comptes) → pagination simple `range`. Pas d'optimisation d'index
  au-delà de ce qu'`auth.users` fournit déjà.
