## 0. Contexte

R3c-i introduit la **toute première couche de planification datée** de l'app. Aujourd'hui :
- Les programmes (muscu **et** running) sont des **modèles de séances ordonnées**
  (`sessions.order_index`) — **sans dates ni jours**.
- Il n'existe **aucune table de planification / calendrier** (vérifié : schéma PowerSync + migrations).
- Le planning muscu calendrier (specs muscu 2.4/3.9/3.11) est **spécifié mais non construit** — c'est
  pourquoi la nutrition 4.7 détecte les jours d'entraînement de façon **rétroactive**
  (« faute de planning muscu daté »).
- La « séance du jour » du dashboard (`useNextSession`, widget 7.4) est **muscu uniquement**
  (`useActiveProgram('strength')`, choix par `order_index`) — le running n'y figure pas.

Décisions de cadrage (12/07/2026) :
- **Découpage** : R3c-i = 5.5 + 5.7 seulement ; **5.6 différée** (pas de coordination bâtie sur du vide).
- **Modèle de génération** : **date de début + semaine type** (affecter chaque séance-gabarit à un
  jour de semaine) ; l'app génère les instances datées sur toute la durée du programme.
- **Sémantique des séances du programme** : les séances (ex. les 3 séances du seed « 10 km en
  8 semaines ») forment le **gabarit hebdomadaire répété** chaque semaine. **Progression automatique
  de volume différée** — chaque semaine reprend les cibles du gabarit à l'identique.
- **Vue** : **semaine (7 jours)**.
- **Séance manquée** : **reporter (déplace 1 instance) ou sauter** ; pas de décalage en cascade.
- **Lien tracker** (démarrer une course depuis une séance planifiée) : **différé** (R4/ultérieur,
  comme déjà posé en R3b-i). Le marquage « fait » est **manuel** au MVP.
- **Table de planification** : **générique, pilier-agnostique** (`planned_sessions`) — le planning
  muscu (3.9) et la coordination (5.6) la réutiliseront sans nouvelle table.

## 1. Périmètre à livrer

- **Assistant « Planifier »** : depuis le détail d'un programme running (`running-programs/[id]`),
  un bouton « Planifier » ouvre un écran : choix d'une **date de début** + affectation de **chaque
  séance-gabarit à un jour de semaine** (semaine type). Validation → génération des instances datées
  sur toute la durée (`duration_weeks` × séances-gabarit) + activation du programme (running).
- **Vue semaine (7 jours)** : bande de 7 jours (semaine courante, navigation ← / →), séances placées
  par jour (type, cible, **allure dérivée du profil R3a**) + jours de repos ; **section/bannière
  « séances manquées »** ; actions par séance : **Reporter** (sélecteur de date → déplace cette seule
  instance), **Sauter** (statut `skipped`), **Marquer comme faite** (statut `done` + horodatage).
- **Table de planification générique** `planned_sessions` (instances datées) + repository + logique
  de génération partagée testée.

**Hors périmètre :**
- **Coordination muscu ↔ running** (5.6, alerte 2 séances le même jour) → **différée** (nécessite un
  planning muscu daté — US muscu 3.9). La table générique la prépare.
- **Démarrer une course GPS depuis une séance planifiée** (lien tracker, pré-chargement type+cible,
  passage auto en « fait ») → **différé** (R4/ultérieur).
- **Progression automatique de volume** (10 %/semaine, running.md §3.3 pt 4 / §4.3) → différée.
- **Décalage en cascade** (reporter une séance décale les suivantes) → hors MVP.
- **Auto-détection « fait »** via une course libre le même jour → hors MVP (marquage manuel ;
  les courses libres comptent dans l'historique/statistiques/streak **indépendamment**).
- **Intégration dashboard** (« séance du jour » running via le widget 7.4) → hors périmètre R3c-i.
- **Planning muscu** (US 3.9) → hors périmètre (la table est prête à le recevoir).

## 2. Comportement attendu

1. **Planifier un programme** : sur le détail programme running → « Planifier » → assistant.
   L'utilisateur choisit une date de début et, pour chaque séance-gabarit, un jour de semaine
   (lun→dim). Confirmation → l'app **génère** toutes les instances (`duration_weeks` semaines ×
   séances-gabarit) et **active** le programme.
   L'assistant exige une **durée en semaines** : pré-remplie avec `program.duration_weeks` si défini,
   sinon **saisie obligatoire** — on ne génère jamais avec une durée nulle/implicite.
   **Re-planifier** un programme déjà planifié **remplace intégralement son planning** : toutes ses
   instances **encore `planned`** (passées comme futures — elles n'ont aucun historique à préserver)
   sont soft-deleted, puis régénérées depuis la nouvelle date. Les instances **`done`/`skipped`** sont
   **conservées** (historique). `planRunningProgram` est ainsi **idempotent**.
2. **Consulter la semaine** : vue 7 jours ; chaque jour affiche ses séances (type, cible formatée
   via `useUnits`, allure cible via `sessionTargetPace` + profil R3a, ou invite « définis ton allure
   de réf » si pas de profil) ; jours sans séance = repos. Navigation semaine précédente / suivante.
3. **Séance manquée** : une instance dont `scheduled_date` est **passée** et le statut encore
   `planned` est **« manquée »** ; elle est mise en avant (bannière / section dédiée). Actions :
   - **Reporter** → sélecteur de date → l'instance prend la nouvelle `scheduled_date` (reste `planned`).
   - **Sauter** → statut `skipped`.
   Le badge « manquée » est calculé **par instance** via `isMissed(scheduledDate, status, today)`
   (donc cohérent en case de jour comme dans la bannière) ; la bannière n'est qu'une **agrégation**
   des instances manquées. `today` = **date locale de l'appareil** (`localDayKey(new Date())`, comme le streak).
4. **Marquer comme faite** : action sur une séance (passée ou du jour) → statut `done` + `completed_at`.
5. **Réactif** (`useQuery`) ; **offline-first** (lecture/écriture locale, synchro arrière-plan).

## 3. Règles métier

- **Instance datée** : une `planned_session` référence un **programme** (`program_id`) et une
  **séance-gabarit** (`session_id`) ; le **pilier en découle** (via `sessions`/`programs`, déjà
  pilier-aware) — **jamais dupliqué** sur la table.
- **Date calendaire** : `scheduled_date` est une **date** (pas un timestamp) — une séance « le 15/07 »
  reste le 15/07 quel que soit le fuseau. Génération et report manipulent des dates calendaires
  (pas de dérive de fuseau / DST).
- **Statuts** : `planned` (défaut) → `done` (fait, + `completed_at`) | `skipped` (sauté). Report =
  changement de `scheduled_date`, statut inchangé (`planned`).
- **Convention jour de semaine** : **0 = lundi … 6 = dimanche** (ISO, cohérent UI FR — semaine
  commençant lundi). ⚠️ `Date.getDay()` en JS renvoie 0 = dimanche : la conversion
  (`(getDay() + 6) % 7`) est **imposée** partout (génération, vue semaine, `startOfWeek`).
- **Semaine type** : chaque séance-gabarit est affectée à **un** jour de semaine (0-6, cf. convention).
  Deux séances peuvent tomber le même jour (autorisé, non bloquant au MVP) ; dans la case du jour,
  elles s'affichent **par `order_index` du gabarit** (rendu déterministe). `week_index` (0-based) est
  stocké sur l'instance pour l'affichage et la future progression.
- **« Futur » / re-planification** : le remplacement soft-delete **toutes** les instances `planned`
  du programme (peu importe la date — passées « manquées » comprises, elles n'ont pas d'historique à
  préserver) ; seules `done`/`skipped` survivent. Rend `planRunningProgram` idempotent et évite les
  doublons/orphelines d'un ancien planning.
- **Génération** : durée (semaines) × séances-gabarit instances, à partir de la date de début alignée
  sur les jours affectés. **La durée est toujours connue** (fournie/exigée par l'assistant, cf. §2.1)
  — jamais de génération avec durée nulle.
- **Un seul actif par pilier** : planifier active le programme (réutilise `activateProgram`, déjà
  un-actif-par-pilier). Un seul jeu d'instances running futures à la fois.
- **Marquage manuel** : au MVP, `done` est posé manuellement ; aucun lien automatique avec les courses
  libres (qui continuent d'alimenter historique/records/streak séparément).

## 4. Architecture

- **Migration (🔴 cloud)** : `supabase/migrations/20260712110000_planned_sessions.sql` (timestamp
  **> `20260712100000`** R3b-i, à confirmer au plan) : table `public.planned_sessions`
  (`id`, `owner_id`, `program_id` → programs, `session_id` → sessions, `scheduled_date date`,
  `status text check (status in ('planned','done','skipped')) default 'planned'`, `week_index int`,
  `completed_at timestamptz`, + conventions `created_at`/`updated_at`/`deleted_at` + trigger
  `set_updated_at`), **RLS** `owner_id = auth.uid()` (select/insert/update/delete), index sur
  `(owner_id, scheduled_date)`, `alter publication powersync add table public.planned_sessions`.
- **Sync rules** ([powersync-sync-rules.yaml](../../technical/powersync-sync-rules.yaml)) : ajouter
  `planned_sessions` au bucket **`user_data`** (données propres à l'utilisateur, `owner_id`).
- **Schéma PowerSync local** ([schema.ts](../../../apps/mobile/src/powersync/schema.ts)) : déclarer
  `planned_sessions` (`program_id`/`session_id`/`status`/`scheduled_date` text, `week_index` integer,
  `completed_at` text).
- **`@wellness/shared`** (TDD) : logique **pure** de génération + statut de manque :
  - `generatePlannedSessions({ templateSessions, dayAssignments, startDate, durationWeeks })`
    → `{ sessionId, scheduledDate, weekIndex }[]`. Calcule, pour chaque semaine et chaque séance
    affectée, la date calendaire sur le jour de semaine voulu. Pure, testée (mapping jours,
    nombre de semaines, robustesse fuseau via dates calendaires).
  - `isMissed(scheduledDate, status, today)` → séance passée encore `planned`.
  - **[date.ts]** : réutilise `localDayKey` (**seule** fonction présente aujourd'hui) et **ajoute**
    les helpers de semaine **manquants** (à créer + tester) : `startOfWeek(date)` (lundi),
    `addDays(date, n)`, `weekdayIndex(date)` (0=lundi…6=dimanche via `(getDay()+6)%7`), itération
    7 jours. Toute manipulation reste en **dates calendaires** (pas de dérive fuseau/DST).
- **Repository** (`apps/mobile/src/data/repositories/planned-session-repository.ts`) :
  - `planRunningProgram(programId, { startDate, durationWeeks, dayAssignments })` — **un seul
    `writeTransaction`** englobant les 3 opérations : soft-delete de **toutes** les instances `planned`
    du programme, insertion des instances générées (via `insertWithSyncFields`), et l'activation.
    ⚠️ Vérifier que `activateProgram` (program-repository.ts) peut être appelé **dans** cette
    transaction ; sinon **inliner** sa logique (mise à jour `is_active`) pour garantir l'atomicité —
    un échec partiel ne doit jamais laisser des instances sans programme actif, ni l'inverse.
  - `useWeekPlan(weekStart)` — réactif, instances d'une fenêtre 7 jours jointes au détail de séance
    (type, cible, nom) pour l'affichage + calcul d'allure.
  - `useMissedSessions('running')` — instances passées `planned` (via `isMissed`).
  - `reschedulePlannedSession(id, newDate)` · `skipPlannedSession(id)` · `markPlannedSessionDone(id)`
    (patch `planned_sessions`, mapping camel→snake, soft-delete jamais dur).
- **Écrans** (Expo Router, `useUnits`, i18next) :
  - **Assistant** `running-programs/plan.tsx` (ou route dédiée) : date de début + affectation
    séance→jour (OptionList jours) → `planRunningProgram`.
  - **Vue semaine** `running-planning/index.tsx` : bande 7 jours + séances/jour (type, cible, allure)
    + bannière/section « manquées » + actions (Reporter via sélecteur de date, Sauter, Marquer faite).
  - **Entrée** depuis l'onglet Course (si pilier running actif) + bouton « Planifier » sur le détail
    programme.
- **i18n** FR+EN : `running.planning.{ title, plan, startDate, assignDay, weekOf, restDay, missed,
  reschedule, skip, markDone, done, skipped, empty, noProfileHint }` + jours de semaine (réutiliser
  l'i18n date existant si présent, sinon `common.weekday.*`). Réutilise `running.objective.*` /
  `running.sessionType.*` / `running.programLevel.*`. Parité, aucune chaîne en dur.
