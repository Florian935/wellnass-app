## 1. Périmètre à livrer

Trois capacités, **Android-first**, offline-first, **une nouvelle dépendance native** (`expo-notifications`) :
- **2.6 Rappel streak en danger** : si l'utilisateur n'a **rien fait aujourd'hui**, une notification locale l'invite
  en soirée (heure **configurable**) à ne pas casser sa série. Annulée dès qu'il est actif.
- **2.8 Ne pas déranger** : aucune notification pendant une **fenêtre configurable** (défaut 22h→7h) ; **max N/jour**
  (défaut 3).
- **1.17 Gestion par type** : activer/désactiver chaque type de notification depuis les Réglages.

**Hors périmètre / différé :**
- Notifications **push distantes** (serveur) — tout est **local** au MVP.
- Types au-delà du rappel streak (suggestion de séance, rappel de repas…) — la structure les accueille, non livrés ici.
- Job d'arrière-plan garanti (background-fetch) : le rappel est (re)planifié **à l'ouverture de l'app**
  (limite assumée : sans ouverture dans la journée, pas de rappel — acceptable MVP).
- iOS (Android d'abord ; le code reste cross-platform mais validé Android).

## 2. Modèle de préférences (`notifications`, enrichi)

Nouveau type Zod (`packages/shared/src/settings.ts`), **tolérant** (parse avec défauts) :
```ts
export interface NotificationPrefs {
  streakDanger: boolean;   // rappel streak activé (défaut true)
  reminderHour: number;    // heure du rappel, 0-23 (défaut 20)
  dndEnabled: boolean;     // Ne pas déranger activé (défaut true)
  dndStartHour: number;    // début fenêtre DND, 0-23 (défaut 22)
  dndEndHour: number;      // fin fenêtre DND, 0-23 (défaut 7)
  maxPerDay: number;       // plafond quotidien (défaut 3)
}
```
- `parseNotificationPrefs(raw): NotificationPrefs` — pur, tolérant : accepte l'ancien `{}`/`Record<string,boolean>`,
  borne les heures (0-23), applique les défauts champ par champ. **Testé.**
- Persistance via `updateSettings({ notifications: prefs })` (JSON, offline-first). Adapter le read/write du
  `settings-repository` (aujourd'hui typé `Record<string,boolean>`).

## 3. Comportement

### 2.6 — Rappel streak en danger
- **Déclencheur d'évaluation** : à l'ouverture/retour au premier plan de l'app (et après une activité terminée),
  calculer `activeToday` (`useStreakData`).
- **Règle** : si `streakDanger` activé **et** `activeToday === false` **et** l'heure de rappel (`reminderHour`)
  n'est **pas encore passée** aujourd'hui **et** le créneau n'est pas en DND → **planifier une notification locale
  ponctuelle** aujourd'hui à `reminderHour`. Si `activeToday === true` (ou rappel désactivé) → **annuler** le rappel
  en attente.
- **Contenu** : titre + corps i18n (ex. « Ta série est en danger 🔥 » / « Fais une activité aujourd'hui pour la
  garder »). Tap → ouvre l'app (dashboard).
- **Idempotent** : au plus **un** rappel streak en attente à la fois (on annule puis replanifie).

### 2.8 — Ne pas déranger + max/jour
- **Fenêtre DND** : si `dndEnabled`, aucune notification planifiée pour un instant compris dans
  `[dndStartHour, dndEndHour)` (fenêtre pouvant enjamber minuit, ex. 22→7). Helper pur `isWithinDnd(hour, prefs)`.
- **Max/jour** : ne pas planifier plus de `maxPerDay` notifications pour un même jour (au MVP, 1 type → trivial ;
  helper pur `canScheduleMore(countToday, prefs)` pour l'avenir).
- Ces règles s'appliquent **avant** toute planification.

### 1.17 — Gestion par type
- Section **« Notifications »** dans les Réglages :
  - interrupteur **Rappel streak en danger** (`streakDanger`) ;
  - sélecteur d'**heure de rappel** (`reminderHour`, 0-23) ;
  - interrupteur **Ne pas déranger** (`dndEnabled`) + sélecteurs **début**/**fin** (`dndStartHour`/`dndEndHour`) ;
  - (max/jour : non exposé à l'UI au MVP — défaut 3).
- Chaque changement persiste via `updateSettings` **et** déclenche une **re-planification** (appliquer les
  nouvelles prefs immédiatement).

### Permissions
- À l'init (après login + settings prêts) : demander la permission notifications (Android 13+ `POST_NOTIFICATIONS`),
  créer le **canal Android** (« Rappels »). Si **refusée** → aucune planification, pas de crash ; la section Réglages
  reste visible et peut inviter à activer dans les paramètres système (message informatif).

## 4. Architecture

- **`@wellness/shared`** (pur, testé) : `NotificationPrefs` + `defaultNotificationPrefs()` + `parseNotificationPrefs`
  + helpers `isWithinDnd(hour, prefs)`, `shouldScheduleStreakReminder({ enabled, activeToday, nowHour, reminderHour, prefs })`
  (retourne booléen), `canScheduleMore(countToday, prefs)`. **Aucune dépendance native.**
- **`packages/shared/src/settings.ts`** : remplacer le type `notifications` par `NotificationPrefs` (schéma + défaut).
- **`apps/mobile/src/lib/notifications.ts`** (couche native fine) : wrapper `expo-notifications` —
  `ensurePermissionAndChannel()`, `scheduleStreakReminder(dateOrHour, content)`, `cancelStreakReminder()`,
  `getScheduled()`. Gère permission refusée. Non testé unitairement (natif) — vérifié en revue + device.
- **`apps/mobile/src/data/repositories/notification-repository.ts`** (ou hook) : `useNotificationPrefs()` (lecture),
  `updateNotificationPrefs(patch)` (écriture via `updateSettings`), et **`useStreakReminderScheduler()`** :
  effet qui, sur changement de `activeToday`/prefs/foreground, applique la règle 2.6 (schedule/cancel).
- **UI** : section Notifications dans `settings.tsx` (interrupteurs + sélecteurs d'heure). Le **sélecteur d'heure**
  reste **JS pur** (stepper 0-23 ou liste), **sans nouvelle dépendance** de date-picker natif.
- **Init** : `_layout.tsx` — effet après settings prêts : `ensurePermissionAndChannel()` puis planification initiale.
- **app.json** : plugin `expo-notifications` (+ icône/couleur par défaut si besoin) + `POST_NOTIFICATIONS`.
- **i18n** : `settings.notifications.*` (UI) + `notifications.streakDanger.{title,body}` (contenu) FR/EN à parité.

## 5. Offline / i18n / a11y

- **Offline-first** : tout est local (prefs synchronisées, planification locale). Aucun serveur.
- **i18n** : aucune chaîne en dur ; contenu de notification + libellés Réglages FR/EN.
- **a11y** : interrupteurs et sélecteurs étiquetés.
- **React Compiler** : hooks inconditionnels ; effets de planification idempotents.
