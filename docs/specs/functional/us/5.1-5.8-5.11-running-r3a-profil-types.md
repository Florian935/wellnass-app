## 1. Périmètre à livrer

| # | Élément | Contenu |
|---|---|---|
| 5.1 | **Profil coureur** (donnée synchronisée) | Objectif, niveau, **allure de référence (5 km)**, fréquence hebdo visée. Éditable dans un écran dédié (profil du pilier running). |
| 5.8–5.11 | **Types de séance + allures cibles** | Calcul, à partir de l'allure de réf, des **plages d'allure cible** pour : endurance fondamentale, sortie longue, récupération active, et fractionné (**via VMA dérivée**). Affichés en référence (« mes allures d'entraînement »). |

**Champs du profil coureur** (running.md §2) :
- **Objectif** : `5k` / `10k` / `semi` / `marathon` / `perte_poids` / `endurance`.
- **Niveau** : `debutant` (< 3 mois) / `regulier` (3-12 mois) / `confirme` (> 1 an).
- **Allure de référence** : allure sur 5 km, **saisie manuelle** en V1 (M:SS par km, via `useUnits` → min/km ou min/mi). *(Calcul auto depuis l'historique = ultérieur.)*
- **Fréquence hebdo visée** : 1 à 7 jours.
- **FCmax** : **hors périmètre** (V2, wearables) — toutes les cibles en **allure**.

**Hors périmètre R3a :**
- **Structure détaillée des séances** (ex. « 6×400 m à 95 % VMA, récup 1:30 ») → appartient aux **programmes (R3b)**. R3a calcule les **allures cibles par type**, pas l'éditeur de blocs.
- Programmes, bibliothèque, filtres (R3b) ; planning/calendrier/coordination/séance manquée (R3c) ; guidage vocal/alertes de bloc (ultérieur).
- Intégration onboarding (le profil s'édite dans un écran dédié ; l'ajout au parcours d'onboarding = ultérieur/optionnel).

## 2. Comportement attendu

1. **Écran profil coureur** (accessible depuis les réglages du pilier running / le dashboard) : formulaire objectif / niveau / allure de réf / fréquence, persisté (réactif `useQuery`), pattern identique au **profil nutritionnel** existant.
2. **Section « Mes allures d'entraînement »** : dès qu'une allure de réf est saisie, afficher pour chaque type une **plage d'allure cible** :
   - **Endurance fondamentale** : réf + 60 à 90 s/km.
   - **Sortie longue** : réf + 30 à 60 s/km.
   - **Récupération active** : réf + 90 à 120 s/km. *(running.md §4.4 dit « +90 s/km ou plus » sans borne ; on retient un **plafond d'affichage assumé à +120** pour garder une plage lisible — décision produit à confirmer.)*
   - **Fractionné (VMA)** : plage **95–100 % VMA** — `min` (plus rapide) = allure à **100 % VMA** = `vmaPace` ; `max` (plus lent) = allure à **95 % VMA** = `vmaPace / 0.95` (= allure 5 km de réf). La VMA est **dérivée** de l'allure 5 km.
   Toutes affichées via `useUnits` (min/km ou min/mi selon réglage).
3. **Sans allure de réf** : la section allures affiche un état vide incitant à renseigner l'allure de référence.

## 3. Règles métier

- **Stockage en SI** : l'allure de réf stockée en **secondes par km** (comme `avg_pace_s_per_km` des runs). L'affichage/saisie passe par `useUnits` (déjà en place). Aucune unité codée en dur.
- **Dérivation VMA** : l'allure 5 km ≈ **95 % de l'allure à VMA** (vitesse) → `vmaPaceSPerKm = ref5kPaceSPerKm × VMA_COEFFICIENT` avec **`VMA_COEFFICIENT = 0.95` (constante nommée exportée** depuis `shared`, ajustable). La vitesse VMA est plus élevée → allure VMA plus rapide (plus petite en s/km). Cibles fractionné = allure à `X % VMA` = `vmaPaceSPerKm / (X/100)`.
- **Plages** : chaque type renvoie `{ minSPerKm, maxSPerKm }` (min = plus rapide). Fonctions **pures** dans `@wellness/shared`, testées.
- **Validation saisie** : allure de réf plausible (> 0, dans une fourchette raisonnable, ex. 2:30–12:00 /km) ; vide → pas de calcul (section allures en état vide).
- **Un seul profil coureur par utilisateur** (une ligne).
