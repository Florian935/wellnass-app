# US 8.5 — Admin : gestion de la base d'aliments (CRUD éditorial)

_Spec fonctionnelle. Statut : validée (brainstorming du 13/07/2026, Florian). Branche :
`feature/8.5-gestion-aliments` (depuis `dev`)._

## 1. Contexte & objectif

L'import CSV (US 8.6) remplit la base d'aliments éditoriale (`foods`, `owner_id IS NULL`,
`source = 'library'`) **en masse**. Il manque la **gestion unitaire** : corriger une valeur
erronée, compléter un aliment, en créer un à la main, ou en retirer un du catalogue.

**Objectif** : un espace d'administration « Aliments » où l'éditeur de contenu **liste, recherche,
crée, édite et archive** les aliments éditoriaux. Contenu **éditorial uniquement** ; jamais les
aliments perso / OpenFoodFacts des utilisateurs (`owner_id` renseigné).

## 2. Périmètre

- **Inclus** : écran liste (recherche + filtre catégorie), **création** d'un aliment à l'unité,
  **édition complète** (nom FR/EN, catégorie, kcal, macros, 10 micros), **archivage** (soft-delete
  `deleted_at`). Migration RLS d'écriture éditoriale sur `foods` / `food_translations`. Validateur
  de formulaire pur dans `@wellness/shared` (testé). Réorganisation du routing « Aliments ».
- **Exclu** : validation des aliments **signalés** (→ 8.7, pas encore de « signaler » mobile) ;
  restauration d'un aliment archivé ; vue des aliments utilisateurs ; édition des `portions`
  (conservées telles quelles) ; historique/audit (→ 8.10). Pas de dimension visuelle spécifique
  → **maquette écartée** (formulaire admin, précédent 8.6 / 8.2).

## 3. Migration RLS (checkpoint 🔴) — débloque aussi 8.6

**Constat** : la RLS d'origine ([20260706150001_food_rls.sql](../../../supabase/migrations/20260706150001_food_rls.sql))
n'autorise l'écriture sur `foods` / `food_translations` que pour `owner_id = auth.uid()`. L'écriture
**éditoriale** (`owner_id IS NULL`) n'a **jamais** été rouverte aux éditeurs de contenu (contrairement
aux exercices — migration 8.2 — et aux programmes — migration 8.4). Sans cette migration, ni la
gestion 8.5 ni **l'import 8.6** ne peuvent écrire l'éditorial (l'insert/update est refusé côté cloud).

- Nouvelle migration `…_admin_editorial_foods_rls.sql` : pour `foods` et `food_translations`,
  **drop + recreate** des policies `_insert` / `_update` en ajoutant `or public.is_content_editor()`
  (patron **identique** à [20260713140000_admin_editorial_programs_rls.sql](../../../supabase/migrations/20260713140000_admin_editorial_programs_rls.sql)).
  `public.is_content_editor()` **réutilisée** (définie en 8.2), non recréée.
- Policies `_select` **inchangées** (l'éditorial `owner_id IS NULL` est déjà lisible par tous).
- **Pas de colonne modifiée** → `database.types` inchangé (**pas de `db:types`**). **Pas de sync
  rule à redéployer** (l'archivage passe par `deleted_at`, déjà pris en charge par les buckets).
- Appliquée manuellement par un humain (SQL Editor), une seule fois → répare 8.5 **et** 8.6.

## 4. Objets gérés — rappel du schéma `foods`

`id, owner_id, source, category (enum 9 valeurs), barcode, import_key, kcal_per_100g,
protein/carbs/sugars/fat/saturated_fat/fiber_per_100g, micronutrients (jsonb), portions (jsonb),
created_at, updated_at, deleted_at`. Traductions dans `food_translations (food_id, lang, name)`,
unique `(food_id, lang)`. **Pas de colonne `status`** (les aliments n'ont pas de brouillon/publié,
contrairement aux exos) : un aliment est présent, ou archivé (`deleted_at`).

## 5. Logique partagée — `@wellness/shared/food-form.ts` (pure, testée)

- `validateFoodInput(input: FoodFormInput): { values: FoodFormValues | null; errors: FoodFormError[] }`.
- `FoodFormInput` = champs **saisis en chaîne** (comme un formulaire) : `nameFr`, `nameEn`,
  `category`, `kcalPer100g`, macros (6), micros (10) — tous en `string` (vide = absent).
- `FoodFormValues` = forme validée typée (nombres, `category` typée, `micronutrients` objet).
- `FoodFormError` : `{ field, reason }` (raison = clé i18n ou message court).
- Règles : `nameFr` / `nameEn` requis (non vides) ; `category` ∈ `FOOD_CATEGORIES` ;
  `kcalPer100g` requis, nombre ≥ 0 ; macros optionnelles, si présentes nombre ≥ 0 ;
  micros optionnels, si présents nombre ≥ 0 (validés via `micronutrientsSchema`, seules les clés
  renseignées sont conservées). Réutilise `FOOD_CATEGORIES` / `MICRONUTRIENT_KEYS` / `micronutrientsSchema`.
- Décimales : point **et** virgule tolérés (`"0,3"` → `0.3`), comme la saisie mobile.

## 6. Couche data admin — `data/foods.ts` (étendu, supabase-js)

- `listEditorialFoods(): { rows: AdminFoodRow[]; error }` — `owner_id IS NULL`, `deleted_at IS NULL`,
  jointure `food_translations(lang, name)`, tri `created_at desc`. `AdminFoodRow` =
  `{ id, category, kcalPer100g, importKey, createdAt, nameFr, nameEn }`.
- `getFood(id): { food: FoodDetail | null; error }` — éditorial + non archivé ; ligne + FR/EN +
  macros + micros + `portions`/`barcode`/`import_key` (préservés).
- `saveFood(input): { id; error }` — **insert si création** (UUID client, `owner_id NULL`,
  `source 'library'`, `portions []`), **update si édition** (ne touche **que** les colonnes du
  formulaire → `portions` / `import_key` / `barcode` intacts). Puis upsert des 2 traductions
  (`onConflict = food_id,lang`). Séquentiel, idempotent (ré-essai sûr).
- `archiveFood(id): { error }` — `update deleted_at = now()` sur `foods` **et** ses
  `food_translations` (séquentiel). Éditorial uniquement (`owner_id IS NULL`).
- `importFoods` (8.6) **inchangé**.

## 7. Écrans & routing (web admin)

Réorganisation de l'espace « Aliments » : la **liste devient le hub** (comme les exercices).

- `/foods` → **`FoodsScreen`** (liste). Table : nom FR, catégorie (traduite), kcal/100 g, date de
  création. Recherche par nom (FR/EN, insensible casse). Filtre par catégorie. Boutons
  **« Nouvel aliment »** (→ `/foods/new`) et **« Importer un CSV »** (→ `/foods/import`). Par ligne :
  **Éditer** (→ `/foods/:id`) et **Archiver** (avec `window.confirm`). États loading / vide / erreur.
- `/foods/import` → `FoodImportScreen` (écran 8.6, **déplacé** ; son éventuel retour pointe `/foods`).
- `/foods/new` et `/foods/:id` → **`FoodEditScreen`** (création / édition). Formulaire : nom FR, nom
  EN, catégorie (select), kcal, section macros (6 champs), section micros (10 champs, unités
  affichées). `import_key` affichée en lecture seule si présente. Bouton Enregistrer → validation
  (`validateFoodInput`) ; erreurs par champ ; succès → retour liste. Annuler → retour liste.
- Toutes gated **`content_editor` / super_admin** (`RequireContentEditor`), nav masquée sinon.
- Nav : l'entrée **« Aliments »** pointe désormais `/foods` (la liste).

## 8. i18n (admin FR)

Enrichir `foods` dans `apps/admin/src/i18n/fr.ts` : titres liste, colonnes, recherche, filtre,
boutons, confirmation d'archivage, libellés de formulaire (macros/micros + unités), noms de
catégories, messages d'erreur/succès, états vide/chargement. Back-office **FR uniquement** (l'app
mobile est bilingue, pas l'admin). Les libellés d'import 8.6 existants sont conservés (déplacés sous
la même clé si besoin).

## 9. Erreurs & cas limites

- Nom FR ou EN vide, catégorie non choisie, kcal vide/non numérique/négatif → erreur par champ,
  pas d'écriture.
- Macro / micro non numérique ou négatif → erreur sur le champ concerné.
- Édition d'un aliment qui n'existe pas / archivé entre-temps → message, retour liste.
- Échec réseau/DB (insert/update/archive) → message d'erreur non bloquant, l'action peut être retentée.
- Archivage : confirmation obligatoire ; l'aliment disparaît de la liste (et de la biblio mobile via
  `deleted_at`). Les entrées de journal déjà enregistrées (snapshot) ne sont pas affectées.
- Un aliment **importé** (avec `import_key`) édité puis ré-importé par CSV : l'upsert 8.6 par
  `import_key` **réécrase** les champs importés (comportement attendu — le CSV fait foi).
