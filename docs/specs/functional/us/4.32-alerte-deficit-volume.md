# US 4.32 — Alerte croisée « déficit calorique + fort volume muscu »

_Spec fonctionnelle. Statut : validée (brainstorming du 15/07/2026, Florian). Branche :
`feature/4.32-alerte-deficit-volume` (depuis `dev`). Première **stat croisée inter-piliers**
(muscu ↔ nutrition) — Phase A du catalogue d'analyses : **déterministe, gratuite, offline, sans IA**._

## 1. Contexte & objectif

Le différenciateur produit est **l'intégration des piliers** (décision H). Cette US livre le premier
signal croisé **muscu ↔ nutrition** : prévenir l'utilisateur quand, sur une semaine, il **sous-mange
nettement par rapport à son objectif** **tout en s'entraînant beaucoup** en musculation — signal de
sous-alimentation face à la charge (risque de récupération/contre-performance).

La **logique cœur existe déjà** dans `packages/shared/src/bodyweight.ts` (`shouldAlertDeficitVolume`,
`averageIntake`, seuils `DEFICIT_ALERT_RATIO`/`HIGH_VOLUME_THRESHOLD`). Le périmètre de l'US est donc
surtout : **encapsuler la règle d'affichage (fonction pure testée)**, **câbler les entrées** depuis les
vraies données, et **exposer** l'alerte sous forme de **widget dashboard conditionnel**.

> **⚠️ Existant à remplacer.** Une **première version** de cette alerte est **déjà en prod** (commit
> `193c5ff`, PR #23) sur l'écran **Stats nutrition** ([nutrition-stats.tsx](../../../apps/mobile/src/app/nutrition-stats.tsx),
> ~lignes 57-107) : elle appelle `shouldAlertDeficitVolume` + `averageIntake` + une requête SQL brute
> du volume muscu 7 j (`set_type != 'warmup'`), et affiche un **message statique** (`stats.deficitAlert`)
> **sans** le `%`, **sans** règle « ≥ 4 jours loggés », **sans gating piliers**. **Décision (Florian,
> 15/07/2026) : la déplacer sur le dashboard** — retirer l'alerte de l'écran Stats et la remonter en
> widget avec les règles renforcées ci-dessous. _(NB : `TODO.md` marque à tort 4.32 comme « différé » ;
> à corriger. Catalogue : MN-02 passe de ✅ « existe » à ✅ après migration.)_

## 3. Règles métier

L'alerte est **active** (widget affiché) si **toutes** ces conditions sont vraies :

1. **Piliers** : musculation **et** nutrition sont **tous deux activés** (`user_settings.active_pillars`).
2. **Données suffisantes** : au moins **4 des 7 derniers jours** comportent des apports loggés
   (`kcal > 0`). En dessous → pas d'alerte (données insuffisantes).
3. **Déficit important** : la **moyenne des apports** (calculée **uniquement sur les jours loggés**,
   jamais sur des jours vides comptés à 0) est **≥ 15 % sous l'objectif calorique de base** du profil
   (`DEFICIT_ALERT_RATIO`).
4. **Fort volume muscu** : le **volume muscu des 7 derniers jours** (Σ reps × charge des séries
   **non-échauffement**, `set_type != 'warmup'`) est **≥ 8000** (`HIGH_VOLUME_THRESHOLD`). _(Calcul en
   SQL dans la requête dédiée — voir §5 ; pas via `computeVolume`.)_

Précisions :
- **Fenêtre** : 7 jours glissants (jusqu'à aujourd'hui inclus), en **jour local**.
- **Objectif** : l'objectif **de base** du profil nutritionnel (pas la cible ajustée jour-de-séance —
  le bonus est journalier, on compare la moyenne hebdo à la cible de base).
- **Seuils** : conservés tels quels (heuristiques `DEFICIT_ALERT_RATIO = 0.15`,
  `HIGH_VOLUME_THRESHOLD = 8000`), **documentés comme ajustables** (une version future pourra rendre le
  seuil de volume **relatif** à la moyenne de l'utilisateur — hors périmètre ici).
- **Ton** : **informatif, non prescriptif** (décision H). Message factuel + nuance douce sur la
  récupération. Le `deficitPct` (arrondi) est injecté dans la copie.

## 4. Logique partagée — `@wellness/shared` (pure, testée)

**Réutilise** l'existant dans `bodyweight.ts` (`shouldAlertDeficitVolume`, `averageIntake`,
`DEFICIT_ALERT_RATIO`, `HIGH_VOLUME_THRESHOLD`, type `Nutrients`). _(Le volume muscu est calculé en SQL
côté hook, §5 — pas via `computeVolume`.)_

**Ajoute** une fonction qui encapsule **toute la règle d'affichage** (centralise le « ≥ 4 jours » et
la moyenne sur jours loggés, pour être testable) :

```ts
export const MIN_LOGGED_DAYS = 4; // sur 7

export type DeficitVolumeAlert = {
  show: boolean;
  deficitPct: number;   // % d'écart sous l'objectif, arrondi (0 si pas d'alerte)
  loggedDays: number;   // nb de jours avec apports loggés (0..7)
};

/**
 * Règle d'affichage de l'alerte croisée déficit + fort volume (déterministe).
 * `loggedDailyKcals` = kcal totales des SEULS jours loggés de la fenêtre 7 j (tableau **épars** :
 * un élément par jour ayant ≥ 1 entrée — aligné sur la forme déjà renvoyée par le repository).
 */
export function computeDeficitVolumeAlert(params: {
  loggedDailyKcals: ReadonlyArray<number>; // jours loggés uniquement (filtrage fait en amont)
  targetKcal: number;
  weeklyVolume: number;
}): DeficitVolumeAlert;
```

Règles internes : `loggedDays = loggedDailyKcals.length` ; si `loggedDays < MIN_LOGGED_DAYS` **ou**
`targetKcal <= 0` → `{ show: false, deficitPct: 0, loggedDays }` ; sinon `avgDailyKcal = moyenne(
loggedDailyKcals)`, `deficitPct = round((target − avg) / target × 100)`,
`show = shouldAlertDeficitVolume({ avgDailyKcal, targetKcal, weeklyVolume })`. **Aucune I/O** (pur).

_Le tableau étant déjà épars (jours loggés uniquement), pas de padding/zéro à 7 : `loggedDays` est
simplement sa longueur — plus simple et conforme à la lecture existante._

## 5. Câblage — hook `useDeficitVolumeAlert` (mobile, `dashboard-repository`)

- Lit l'**objectif de base** depuis le profil nutritionnel (cible calorique, **non** ajustée

- Lit le **volume muscu des 7 derniers jours** via une **requête dédiée fenêtre glissante 7 j** sur

  `nutrition-stats.tsx`** (elle y disparaît, on la déplace dans le repository). ⚠️ Ne **pas** réutiliser
  `useWorkoutHistory` (volontairement léger, sans séries) ni `useMuscleVolumeThisWeek` (semaine **ISO**,

- **Gating piliers** : si muscu **ou** nutrition n'est **pas** activé (`active_pillars`), renvoie
  `{ show: false, ... }` sans requêter inutilement.
- Compose le tout via `computeDeficitVolumeAlert` et renvoie `DeficitVolumeAlert`. Le hook ne fait
  **que** de la lecture (aucune écriture).

## 8. Cas limites

- **< 4 jours loggés / 7** → pas d'alerte (données insuffisantes).
- **Un pilier inactif** (muscu ou nutrition) → pas d'alerte, widget absent.
- **Objectif calorique ≤ 0 / non défini** → pas d'alerte.
- **Volume muscu nul** (aucune séance sur 7 j) → pas d'alerte (pas « fort volume »).
- **Jours non loggés** comptés à 0 → **exclus** de la moyenne (ne créent pas de faux déficit).
- **Offline** : 100 % données locales → fonctionne hors-ligne, réactif à toute nouvelle saisie.
