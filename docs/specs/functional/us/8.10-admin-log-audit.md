# US 8.10 — Admin : log d'audit des actions

_Spec fonctionnelle. Statut : validée (brainstorming du 14/07/2026, Florian). Branche :
`feature/8.10-admin-log-audit` (depuis `dev`). Première des trois US de gouvernance admin
restantes ; ordre acté : **8.10 (audit) → 8.7 (modération) → 8.8 (utilisateurs)**._

## 1. Contexte & objectif

Le back-office (`apps/admin`) permet déjà des actions qui engagent le **contenu partagé** et les
**droits** : attribution/révocation de rôles (8.9), CRUD éditorial des exercices (8.2), des
programmes (8.4) et des aliments (8.5) + import CSV (8.6). Aucune de ces actions n'est **tracée** :
impossible de savoir qui a archivé un aliment, publié un programme ou accordé un rôle, ni quand.

**Objectif** : un **journal d'audit append-only et non supprimable** qui enregistre chaque écriture
éditoriale et de rôle, plus un **écran de consultation** réservé au super_admin (liste + filtres).
Finalité = **responsabilité et traçabilité entre coéquipiers de confiance** (et débogage), pas
défense contre un admin malveillant (voir §3, modèle de menace).

## 2. Périmètre

- **Inclus** : nouvelle table `audit_log` (web/admin uniquement, hors PowerSync) + RLS + trigger
  d'immuabilité ; **capture applicative** (`logAudit`) branchée sur les mutations existantes
  (rôles, exercices, programmes, aliments + import) ; logique pure `@wellness/shared/audit.ts`
  (testée) ; couche I/O `apps/admin/src/data/audit.ts` (`logAudit` + `listAudit`) ; **écran
  `/audit`** super_admin (liste anti-chronologique + filtres acteur / type d'action / période) ;
  i18n admin FR.
- **Exclu** : audit des **lectures** (consultations d'écran) ; audit des actions **utilisateur
  mobile** ; diff/instantané des valeurs modifiées (détail limité à qui/quoi/cible/quand + libellé,
  voir §5) ; export du journal ; purge/rétention (le log est conservé indéfiniment — exigence « non
  supprimable ») ; capture par **triggers** sur les tables éditoriales (approche écartée, voir §3) ;
  résolutions de signalements (8.7) et bans (8.8) — **non implémentés ici**, mais le schéma est
  générique pour les accueillir **sans migration** ; **sous-éditions de structure d'un programme**
  (ajout/suppression/réordonnancement de séances et de plans d'exercice) — non tracées
  individuellement, l'audit est à la **granularité de l'entité** (création / màj méta / publication /
  archivage du programme), voir §7.
- **Maquette écartée** : écran de liste + filtres classique du back-office (précédents 8.2 / 8.5),
  aucune dimension visuelle spécifique.

## 3. Approche de capture (arbitrage validé) & modèle de menace

**Capture applicative (approche A)** retenue, contre les triggers SQL (B) et l'hybride (C).

- Chaque couche data de l'admin appelle `logAudit(...)` **après une mutation réussie**. La ligne
  d'audit porte l'**intention métier** (`program.publish`, `food.archive`…), un **libellé lisible**
  et, pour un import en masse, **une seule** entrée (`details.count`) au lieu de N lignes.
- **Modèle de menace assumé** : l'admin tourne sur la **clé anon** (pas de `service_role`) ; le même
  client exécute la mutation **et** le log. On ne peut donc pas garantir côté client qu'une action
  soit toujours journalisée, ni empêcher techniquement la forge d'une entrée. La RLS limite
  l'écriture aux admins et impose `actor_id = auth.uid()` (acteur honnête). La garantie est
  **best-effort**, adaptée à une équipe interne de confiance. Durcissement futur possible sans
  rien casser : ajouter un trigger infalsifiable sur `user_roles` (bascule vers l'approche C).
- Les triggers (B) ont été écartés : ils capturent la mécanique ligne à ligne (pas l'intention),
  rendent le libellé lisible pénible (jointure traductions) et transforment un import CSV en dizaines
  de lignes bruyantes.

## 4. Migration (checkpoint 🔴) — `audit_log` + RLS + immuabilité

Nouvelle migration `…_admin_audit_log.sql`. Table **web/admin uniquement** — **hors** publication
PowerSync (comme `user_roles`, le mobile n'en a pas besoin).

```
create table public.audit_log (
  id           uuid primary key default gen_random_uuid(),
  actor_id     uuid,                            -- PAS de FK cascade : la trace survit à la suppression du compte
  actor_email  text,                            -- instantané de l'email de l'admin au moment de l'action
  action       text not null,                   -- ex. 'exercise.archive', 'program.publish', 'role.grant', 'food.import'
  target_table text,                            -- 'exercises' | 'programs' | 'foods' | 'user_roles' (nullable)
  target_id    uuid,                             -- id de la ligne touchée (nullable : import en masse)
  target_label text,                            -- libellé lisible : « Développé couché », « moderator → <user_id> »
  details      jsonb not null default '{}',      -- contexte léger : {count: 200} import, {role, targetUserId}…
  created_at   timestamptz not null default now()
);
create index audit_log_created_at_idx on public.audit_log (created_at desc);
create index audit_log_actor_idx      on public.audit_log (actor_id);
create index audit_log_action_idx     on public.audit_log (action);
```

**RLS & immuabilité :**
- `enable row level security`.
- `select` : **super_admin uniquement** (`using (public.is_super_admin())`).
- `insert` : tout admin, `with check (public.is_admin() and actor_id = auth.uid())`.
- **Aucune** policy `update` ni `delete` → append-only de fait via l'API (super_admin compris).
- **Filet d'immuabilité** : trigger `before update or delete` levant une exception
  (`audit_log_immutable`), pour verrouiller même si une policy `update`/`delete` est ajoutée par
  erreur plus tard.
- Prérequis autosuffisants (patron 8.9) : `create extension if not exists pgcrypto` et réutilisation
  de `public.is_admin()` / `public.is_super_admin()` (définies en 8.9, **non recréées**).
- **Pas** d'ajout à la publication `powersync`. **Régénérer `db:types`** après apply (nouvelle table).

## 5. Logique partagée — `@wellness/shared/audit.ts` (pure, testée)

- `AuditAction` : union typée des actions tracées —
  `'role.grant' | 'role.revoke' | 'exercise.create' | 'exercise.update' | 'exercise.archive' |
  'exercise.publish' | 'program.create' | 'program.update' | 'program.archive' | 'program.publish' |
  'food.create' | 'food.update' | 'food.archive' | 'food.import'`.
  _(Symétrie exos/programmes : les deux exposent un `setStatus` de publication → les deux sont
  tracés — `exercise.publish` et `program.publish`.)_
- `AUDIT_ACTIONS: readonly AuditAction[]` — liste ordonnée (pour le filtre de l'écran).
- `auditEntrySchema` (Zod) : forme de l'entrée à insérer (`action` ∈ union, `targetTable?`,
  `targetId?` uuid, `targetLabel?`, `details` objet par défaut `{}`). `actor_id`/`actor_email`/
  `created_at` ne sont **pas** dans l'input (renseignés par la couche I/O / la base).
- `auditActionLabelKey(action): string` — clé i18n FR du libellé lisible de l'action (ex.
  `'audit.action.program.publish'`). Mapping exhaustif sur l'union (garde de complétude au type).
- **Aucune** dépendance Supabase ni I/O ici (pur, testable Vitest — patron `food-form.ts`).

## 6. Couche data admin — `apps/admin/src/data/audit.ts` (supabase-js)

- `logAudit(entry: AuditInput): Promise<{ error: unknown }>` :
  - valide `entry` via `auditEntrySchema` ;
  - récupère l'acteur courant (`supabase.auth.getUser()` → `actor_id`, `actor_email`) ;
  - insère dans `audit_log`.
  - **Best-effort & non bloquant** : ne **lève jamais** ; en cas d'échec (validation, session,
    réseau, RLS), journalise un `console.warn` et renvoie `{ error }`. **Ne remonte pas** l'erreur
    aux appelants de façon bloquante — l'action métier reste réussie (voir §7).
- `AuditLogRow = Database['public']['Tables']['audit_log']['Row']`.
- `listAudit(params): Promise<{ rows: AuditLogRow[]; error }>` — `params = { actorId?, action?,
  from?, to?, limit?, before? }`. Filtres optionnels (`actor_id`, `action`, plage `created_at`),
  tri `created_at desc`, pagination par **curseur** (`before` = `created_at` de la dernière ligne)
  + `limit` (défaut 50). Tolérant aux erreurs (`{ rows: [], error }`, patron `roles.ts`).

## 7. Points de capture (mutations existantes instrumentées)

Un appel `logAudit(...)` **après succès** de chaque mutation, jamais avant, jamais bloquant :

- `data/roles.ts` → `grantRole` ⇒ `role.grant` ; `revokeRole` ⇒ `role.revoke`.
  `targetTable='user_roles'`, `targetId=` id de l'attribution, `details={ role, targetUserId }`,
  `targetLabel='<role> → <targetUserId>'` (l'email de la cible n'est **pas** disponible en anon).
  ⚠️ `grantRole` **ne renvoie pas** l'id d'attribution aujourd'hui : le plan capte le `logAudit`
  **dans** `grantRole`, en ajoutant `.select('id')` sur l'insert (et en réutilisant l'id de la ligne
  réactivée le cas échéant). Signature publique inchangée. Si l'id reste indisponible, `targetId=null`
  (dégradation acceptée).
- `data/exercises.ts` → `saveExercise` : `exercise.create` (création) ou `exercise.update`
  (édition) ; `archiveExercise` ⇒ `exercise.archive` ; `setStatus` passant à publié ⇒
  `exercise.publish`. `targetLabel=` nom FR de l'exercice (déjà en main dans la couche).
- `data/programs.ts` → `createEditorialProgram` ⇒ `program.create` ; `updateProgramMeta` ⇒
  `program.update` ; `archiveProgram` ⇒ `program.archive` ; `setStatus` passant à publié ⇒
  `program.publish`. `targetLabel=` nom FR du programme. _(Les sous-éditions de structure —
  `addSession`/`updateSession`/`removeSession`/`reorder*`/`*ExercisePlan` — ne sont **pas** tracées
  individuellement : granularité à l'entité programme, voir §2 Exclu.)_
- `data/foods.ts` → `saveFood` : `food.create` (insert) ou `food.update` (update) ;
  `archiveFood` ⇒ `food.archive` ; `importFoods` (8.6) ⇒ **une** entrée `food.import`
  (`targetTable='foods'`, `targetId=null`, `details={ count }`).

**Discriminant création vs édition** : pour `saveFood` / `saveExercise` (upsert unique décidant
insert/update en interne), l'action est `*.create` **si `input.id` est absent** (parcours écran
`/…/new`), sinon `*.update` (parcours `/…/:id`). Même règle pour les deux devs.

**Règle transverse** : l'échec d'un `logAudit` ne doit **jamais** faire échouer ni annuler la
mutation métier (audit = observabilité, pas transaction). Les mutations restent inchangées dans leur
comportement de retour actuel.

## 8. Écran & routing (web admin)

- Nouvelle route **`/audit`** → `AuditScreen`, gated **super_admin** (`RequireSuperAdmin`, patron
  `RolesScreen` / 8.9). Nav : entrée **« Journal d'audit »** visible pour le super_admin uniquement.
- Liste anti-chronologique. Colonnes : **date + heure** (`JJ/MM/AAAA HH:MM`), **acteur**
  (`actor_email` sinon repli `actor_id`), **action** (libellé FR via `auditActionLabelKey`),
  **cible** (`target_label` sinon `target_table`/`target_id`).
- **Filtres** : acteur (liste des acteurs présents), type d'action (`AUDIT_ACTIONS`), période
  (date de début / fin). Bouton « Réinitialiser ».
- Pagination « Charger plus » (curseur `created_at`). États **chargement / vide / erreur**
  (« Aucune action enregistrée »).

## 9. i18n (admin FR)

Nouvelle section `audit` dans `apps/admin/src/i18n/fr.ts` : titre de l'écran, entrée de nav, noms de
colonnes, libellés de filtres, bouton « Charger plus » / « Réinitialiser », états vide/chargement/
erreur, et le **mapping des libellés d'action** (`audit.action.*`, un par valeur de `AuditAction`).
Back-office **FR uniquement** (l'app mobile est bilingue, pas l'admin).

## 10. Erreurs & cas limites

- **Échec de `logAudit`** (réseau, RLS, session expirée) → action métier **réussie quand même**,
  `console.warn`, aucune entrée écrite (best-effort assumé).
- **Acteur sans email** (cas improbable) → `actor_email` null, l'écran affiche `actor_id`.
- **Compte acteur supprimé** ultérieurement → `actor_id` peut ne plus correspondre à un compte
  vivant ; `actor_email` (snapshot) reste affiché. Pas de FK cascade → la ligne d'audit persiste.
- **Import CSV** → exactement **une** entrée `food.import` avec `details.count`, même si 0 ligne
  importée (count=0 possible). Pas d'entrée par aliment.
- **Tentative de modification/suppression** d'une entrée (via API) → refusée (aucune policy) **et**
  levée par le trigger d'immuabilité si une policy venait à exister.
- **Non-super_admin** ouvrant `/audit` → `AccessDenied` (route gated) ; `select` refusé par la RLS
  de toute façon.

## 12. Definition of Done

- Chaque mutation admin (rôle, exercice, programme, aliment, import) écrit une entrée d'audit ; un
  import CSV = une seule entrée.
- Écran `/audit` (super_admin) : liste anti-chronologique + filtres acteur / action / période +
  pagination + états vide/erreur.
- Écriture append-only : aucune modification/suppression possible (RLS + trigger).
- typecheck / lint / build verts ; nouveaux tests shared verts.
- **Reste checkpoint 🔴 Florian** : appliquer la migration `audit_log` (table + RLS + trigger) sur
  le cloud via `npm run db:push`, cocher [MIGRATIONS.md](../../../supabase/MIGRATIONS.md),
  régénérer `npm run db:types`, puis recette web (déclencher une action de chaque type → entrées
  visibles et correctes dans `/audit` ; tenter une modif d'entrée → refus ; filtres OK).
