# US 8.1a — Admin : fondation (scaffold + auth + shell protégé) [V0.7, Fondation-1]

> Poser le **back-office web** (`apps/admin`) : app Vite+React, **authentification Supabase**, **shell protégé**
> (routes privées + layout + page d'accueil placeholder). **100 % client, aucune migration, aucun cloud** — testable
> en navigateur immédiatement. Le **gate par rôle** (table `user_roles` + RLS) = **Fondation-2** (lot suivant, 🔴 cloud).
> Branche : `feature/admin-f1-scaffold-auth` · Date : 13/07/2026 · **Statut : à valider (pas de code avant validation).**

## 0. Contexte (exploration)

- `apps/admin` = **stub** (package.json sans framework, `src/index.ts` quasi vide, tsconfig). **Greenfield** web.
- `@wellness/shared` s'importe **en source TS** (`exports: "./src/index.ts"`, `type: module`) — Vite le consomme
  directement (workspace npm), sans build. `database.types.ts` réutilisable.
- Auth : `supabase-js ^2.110.0` déjà utilisé côté mobile (`apps/mobile/src/lib/supabase.ts`). Côté web : env
  **`VITE_*`** + session **`localStorage`** (défaut). **Clé anon** (client-safe) — **jamais** de `service_role`.
- CI (`.github/workflows/ci.yml`) itère les workspaces (`typecheck`/`lint`/`test`) → l'app admin sera prise en
  compte si elle expose ces scripts. Monorepo npm workspaces (`apps/*`, `packages/*`).

## 1. Périmètre à livrer (Fondation-1)

Une app web admin **qui démarre, se connecte, et protège ses routes** :
- **Scaffold** Vite + React + TypeScript dans `apps/admin` (dev/build/preview/typecheck/lint).
- **Auth Supabase** : écran de connexion (email + mot de passe), session persistée (localStorage), déconnexion.
- **Shell protégé** : routes privées (redirection vers `/login` si non connecté), layout (barre latérale/entête +
  bouton déconnexion) et une **page d'accueil placeholder** (« Back-office — bientôt : gestion du contenu »).
- **Réutilisation** de `@wellness/shared` (types) pour prouver l'intégration monorepo.

**Hors périmètre (lots suivants) :**
- **Autorisation par rôle** (qui est admin) : **Fondation-2** (`user_roles` + RLS + gate). En F1, **toute personne
  authentifiée** atteint le shell — acceptable car F1 **n'expose aucune donnée ni action admin** (placeholder seul ;
  aucune policy RLS élevée ; un utilisateur lambda n'y voit rien de plus que ce que le RLS lui autorise déjà).
- CRUD de contenu (exercices/aliments/programmes), upload média, import CSV, modération, audit, gestion users
  (8.2→8.10) — lots ultérieurs.
- Déploiement/hébergement (build statique livré ; où l'héberger = ultérieur).
- Inscription/reset de compte depuis l'admin (les comptes existent via l'app ; l'admin ne fait que **se connecter**).

## 2. Comportement attendu

- **Non connecté** : toute route privée redirige vers **`/login`**. La page login propose email + mot de passe +
  bouton « Se connecter ». Erreur d'identifiants → message clair (i18n ou texte FR, cf. §5). Chargement pendant l'appel.
- **Connexion réussie** : `supabase.auth.signInWithPassword` → session persistée (localStorage) → redirection vers
  l'accueil admin (`/`). Au rechargement de page, la session est **restaurée** (pas de reconnexion).
- **Shell** : layout persistant (entête avec titre « Wellness Admin » + e-mail de l'utilisateur + **Déconnexion**) ;
  zone de contenu routée. Page d'accueil = placeholder (message + éventuelle liste des futurs modules, non cliquables).
- **Déconnexion** : `supabase.auth.signOut()` → retour à `/login`.
- **Écoute de session** : `supabase.auth.onAuthStateChange` met à jour l'état (connexion/déconnexion/refresh) ;
  nettoyage de l'abonnement au démontage.

## 3. Architecture

- **Scaffold** (`apps/admin`) :
  - `package.json` : deps `react`, `react-dom`, `react-router-dom`, `@supabase/supabase-js`, `@wellness/shared` ;
    devDeps `vite`, `@vitejs/plugin-react`, `typescript`, types React, ESLint (config web React). Scripts :
    `dev` (vite), `build` (`tsc -b` + `vite build`), `preview`, `typecheck` (`tsc --noEmit`), `lint`.
  - `index.html`, `src/main.tsx` (mount + Router), `vite.config.ts` (`@vitejs/plugin-react`), `tsconfig` app (lib
    `DOM`, jsx react-jsx ; étend la base si compatible). **Ne pas** casser le typecheck racine des autres workspaces.
  - **ESLint** : config web React (l'app mobile utilise `eslint-config-expo`, inadaptée ici) — config minimale
    (react-hooks, TS). S'assurer que `npm run lint` racine passe (l'app expose son propre `lint`).
- **Supabase** (`src/lib/supabase.ts`) : `createClient<Database>(import.meta.env.VITE_SUPABASE_URL,
  import.meta.env.VITE_SUPABASE_ANON_KEY, { auth: { persistSession: true, autoRefreshToken: true } })`.
  `Database` importé de `@wellness/shared`. **Aucune clé en dur** : `.env` local (gitignore) + **`.env.example`** commité.
- **Auth** : contexte/hook `useAuth()` (session courante, `signIn`, `signOut`, `loading`) basé sur
  `onAuthStateChange` + `getSession`. `RequireAuth` (wrapper de route) redirige si pas de session.
- **Routing** (`react-router-dom`) : `/login` (public), `/` + futures routes (privées sous `RequireAuth` + layout).
- **UI** : composants simples (login form, layout, placeholder). Style **fonctionnel** propre (accent terracotta de
  la marque `#dd6e40` possible), thème clair lisible. Pas de lib UI lourde imposée.
- **Env & secrets** : `.env.example` (`VITE_SUPABASE_URL=`, `VITE_SUPABASE_ANON_KEY=`) ; `.gitignore` couvre
  `apps/admin/.env*`. **Ne jamais committer** de vraie clé.

## 4. Sécurité (F1)

- **Authentification seule** (pas d'autorisation) : F1 vérifie qu'un utilisateur est **connecté**, pas qu'il est
  **admin** (→ F2). Justifié : aucune donnée/action sensible en F1 (placeholder) ; le RLS existant protège déjà
  toutes les tables (un user lambda connecté à l'admin ne peut rien lire/écrire qu'il ne pouvait déjà).
- **Clé anon uniquement** côté client ; RLS = frontière de sécurité. **`service_role` interdit** dans l'app.
- Le **gate admin réel** (bloquer les non-admins à l'entrée) arrive en **F2** avant tout écran de contenu.

## 5. i18n
- L'admin est **interne** (FR d'abord). Option retenue : **textes FR** en dur *centralisés* (petit module de libellés)
  au MVP admin — l'i18n complète (i18next) n'est **pas** requise pour la fondation (à réévaluer si l'admin grossit).
  _(À confirmer en validation : FR-only centralisé vs i18next dès le départ.)_
