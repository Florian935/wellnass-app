# US 3.9 — Planning musculation daté + calendrier unifié (coordination muscu ↔ running)

> Complète le pilier **muscu** (planning calendrier, spec [musculation.md](../musculation.md) §2.4) en
> **réutilisant** l'infra de planification générique bâtie en R3c-i (running). Livre aussi l'**essentiel de
> la coordination 5.6** (calendrier unifié 2 piliers + alerte même-jour). **Aucune migration, aucun
> checkpoint cloud** (`planned_sessions` déjà générique et déployée). Branche : `feature/us3.9-planning-unifie` ·
> Date : 12/07/2026 · **Statut : à valider (pas de code avant validation).**

## 0. Contexte

R3c-i a introduit une **couche de planification datée générique et pilier-agnostique** :
- Table **`planned_sessions`** (déployée cloud) : instance datée `{ program_id, session_id, scheduled_date,
  status planned|done|skipped, week_index, completed_at }` ; le **pilier est hérité** de `sessions`/`programs`.
- Repository `planned-session-repository.ts` : `planRunningProgram` (génération datée en une transaction +
  activation par pilier), `useWeekPlan(weekStart)` (**ne filtre PAS le pilier** — renvoie déjà toutes les
  séances de la fenêtre), `useMissedSessions()` (**filtre `pillar='running'`**), `reschedule`/`skip`/`markDone`.
- Écran `running-planning/` (vue semaine 7 jours + assistant `running-programs/plan.tsx`).

Côté muscu, tout le nécessaire existe déjà : `programs` (`pillar='strength'`), `sessions`, `exercise_plans`,
et les écrans `programs/{index,[id],edit}.tsx`. Il **manque uniquement** de planifier ces programmes sur un
calendrier — c'est pourquoi la nutrition 4.7 détecte les jours d'entraînement de façon **rétroactive**.

Décisions de cadrage (12/07/2026) :
- **Calendrier unifié** : un seul écran « Mon planning » affichant **muscu + running** ensemble (pas deux
  écrans séparés) → livre 3.9 **et** la coordination même-jour (5.6).
- **Affichage d'une séance muscu** : **nom + nombre d'exercices** (ex. « Push · 5 exercices »).
- **Généralisation** de l'infra R3c-i (pilier-agnostique), pas de duplication.
- **Aucune migration / aucun cloud** : `planned_sessions` générique déjà déployée ; séances muscu déjà
  synchronisées. **100 % JS** → simple rebuild pour la recette.

## 1. Périmètre à livrer

- **Généraliser le repository** de planification (pilier-agnostique).
- **Écran unifié « Mon planning »** (`/planning`) : vue semaine 7 jours affichant les séances **muscu et
  running** par jour, distinguées visuellement ; contenu par pilier (running : type/cible/allure ; muscu :
  nom + nb d'exercices) ; **indicateur de coordination** quand un jour porte ≥ 2 séances ; bannière séances
  manquées (tous piliers) ; actions par tap (reporter / sauter / marquer faite).
- **Assistant « Planifier » pilier-aware** : accessible depuis le détail programme **muscu** (`programs/[id].tsx`)
  **et** running (re-câblé). Semaine type (date de début + durée + affectation de chaque séance à un jour).
- **Entrées** : « Mon planning » depuis l'onglet **Muscu** et l'onglet **Course** (si pilier actif).
- **i18n** FR/EN, non-régression running.

**Hors périmètre :**
- **Progression automatique de volume** muscu (musculation.md §2.3 pt 5) → différée.
- **Glisser-déposer** dans le calendrier (musculation.md §2.4) → on garde les actions par **tap** (reporter/sauter).
- **Coordination avancée** (calcul de charge, recommandations de récup) → l'alerte même-jour reste un
  **indicateur doux** non bloquant (décision H, pas d'imposition).
- **Vue mois** ; **démarrer une séance depuis le planning** (lien tracker/séance muscu) → différé.
- **Détection anticipée nutrition 4.7** (basculer de rétroactif à planifié) → US nutrition ultérieure ;
  3.9 en pose la base (données planifiées datées).

## 2. Comportement attendu

1. **Planifier un programme (muscu ou running)** : depuis le détail du programme → « Planifier » → assistant
   (durée en semaines, date de début, affectation de chaque séance-gabarit à un jour de semaine). Confirmation
   → génération des instances datées sur toute la durée + activation du programme (un actif par pilier).
   Re-planifier remplace les instances `planned` du programme (idempotent), conserve `done`/`skipped`.
2. **Consulter « Mon planning »** (vue semaine 7 jours, lun→dim, navigation ← / →) : chaque jour liste **toutes**
   ses séances planifiées, **muscu et running mélangées**, chacune marquée par pilier (icône/couleur) :
   - **running** : type (endurance/fractionné/…), cible (distance/durée via `useUnits`), allure dérivée du profil ;
   - **muscu** : nom de séance (repli « Séance N ») + **« N exercices »**.
   Jours sans séance = repos.
3. **Coordination (5.6)** : si un jour porte **≥ 2 séances actives** (statuts `planned` + `done`, `skipped`
   **exclu**), afficher un **indicateur discret** sur ce jour (ex. « 2 séances ») + éventuel libellé d'attention
   léger. **Non bloquant** (on n'empêche jamais de planifier ; on informe).
4. **Séance manquée** (date passée, statut `planned`, tous piliers) : bannière d'agrégation ; actions **Reporter**
   (aujourd'hui/demain/+7), **Sauter**, **Marquer faite**.
5. **Réactif** (`useQuery`) ; **offline-first** (lecture/écriture locales).

## 3. Règles métier

- **Une séance planifiée = une instance datée** dans `planned_sessions` (générique). Le **pilier** vient de
  `programs.pillar` (jamais dupliqué). Aucune règle running-spécifique ne doit rester dans les hooks de lecture.
- **Contenu par pilier** : la vue dérive l'affichage du pilier — running utilise `session_type`/cibles/allure ;
  muscu utilise le **nombre d'exercices** = `COUNT(exercise_plans WHERE session_id = … AND deleted_at IS NULL)`.
- **Coordination** = « ≥ 2 séances le même jour » (comptage des instances `planned`/`done` d'une même date
  locale). Indicateur informatif ; jamais de blocage (décision H).
- **Semaine type / génération / activation / dates calendaires / idempotence** : **identiques à R3c-i**
  (convention 0=lundi, `scheduled_date` en date calendaire, remplacement des `planned` à la re-planification).
- **Un seul programme actif par pilier** (déjà garanti par l'activation) — planifier un programme muscu
  n'affecte pas le programme running actif, et vice-versa.
- **Manuel/complétion** : marquage « faite » manuel (comme R3c-i) ; pas de lien automatique avec une séance
  réellement effectuée (différé).

## 4. Architecture

- **Aucune donnée nouvelle** : réutilise `planned_sessions`, `programs`, `sessions`, `exercise_plans`
  (tous déployés + synchronisés). **Aucune migration, aucune sync rule, aucun `db:types`.**
- **Repository** (`planned-session-repository.ts`) — généralisation pilier-agnostique, **sans régresser le running** :
  - `planRunningProgram` → **`planProgram(programId, { startDate, durationWeeks, dayAssignments })`** (renommage ;
    logique inchangée, déjà générique + activation par le pilier lu du programme). Mettre à jour le seul appelant
    (assistant). Conserver éventuellement un alias déprécié si utile, sinon migrer l'appel.
  - `PlannedSessionItem` : ajouter **`pillar: Pillar`** et **`exerciseCount: number`** (0 pour running / séances
    sans exercices).
  - `SELECT_PLANNED_BETWEEN` (useWeekPlan) : joindre `programs` pour `p.pillar`, et ajouter un sous-select
    `COUNT` des `exercise_plans` de la séance (`exercise_count`). `useWeekPlan(weekStart)` renvoie donc **tous
    les piliers** enrichis. (Il ne filtrait déjà pas le pilier — pas de régression running.)
  - `SELECT_MISSED_RUNNING` → **`SELECT_MISSED`** : **retirer** le filtre `pillar='running'` (tous piliers) +
    exposer `pillar`/`exercise_count` comme ci-dessus. `useMissedSessions()` → tous piliers.
  - `reschedule`/`skip`/`markDone` : inchangés.
- **Écran** : renommer `running-planning/` → **`planning/`** (route `/planning`), rendu **pilier-aware** :
  chaque carte de jour affiche les séances des 2 piliers avec un rendu conditionnel selon `item.pillar`
  (running : bloc existant ; muscu : nom + « N exercices »), une **puce/icône de pilier**, l'indicateur
  coordination (≥ 2 séances), la bannière manquées, les actions. Réutilise `useUnits`, `Segment`, `Card`,
  `EmptyState`.
- **Assistant** : renommer/généraliser `running-programs/plan.tsx` en assistant partagé recevant `programId`
  (pilier déduit du programme) ; lignes d'affectation montrant le **nom** de séance (muscu) ou le type (running).
  ⚠️ **3 routes à mettre à jour de façon cohérente** (l'assistant utilise un **query-param `?id=`**, pas un path
  param) : (a) le `router.push('/running-programs/plan?id=…')` du détail running → nouvelle route ; (b) **ajouter**
  le même push depuis le détail muscu `programs/[id].tsx` ; (c) le `router.replace('/running-planning')` de fin
  d'assistant → **`/planning`** (route unifiée).
- **Entrées** : bouton « Mon planning » → `router.push('/planning')` depuis **l'onglet Course** (conditionné à
  `activePillars.includes('running')`, gating existant) **et** depuis l'écran/onglet **Muscu** (`(tabs)/strength.tsx`)
  **sans condition** (muscu = pilier socle toujours actif — ne PAS ajouter de gating `activePillars` côté muscu).
- **Route** : renommer `running-planning/` → `planning/` ; dans `app/_layout.tsx`, remplacer
  `Stack.Screen name="running-planning"` par `name="planning"` (retirer l'ancienne) ; mettre à jour l'ancien
  `router.push('/running-planning')` de l'onglet Course → `/planning`. Aucune route morte résiduelle.
- **i18n** : généraliser `running.planning.*` (bloc imbriqué sous `running`) en un **namespace partagé `planning.*`**
  de premier niveau, **avec parité FR/EN**. ⚠️ **Renommage exhaustif** : migrer **toutes** les occurrences
  `running.planning.` → `planning.` dans les 3 fichiers running consommateurs (`running-planning/index.tsx`,
  `running-programs/plan.tsx`, `running-programs/[id].tsx`) **en une passe**, + **grep de contrôle à zéro
  occurrence résiduelle** avant merge. Ajouter les clés muscu (`planning.exerciseCount` pluralisé) + coordination
  (`planning.multipleSameDay`). Réutiliser `running.sessionType.*`/`running.objective.*` côté running.
- **Non-régression running (device-validé)** : après renommage/généralisation, l'écran planning running et
  l'assistant doivent se comporter **à l'identique**. **À vérifier explicitement** (aucune clé i18n cassée,
  aucune route morte, `planProgram` = ex-`planRunningProgram` sans changement de logique).
