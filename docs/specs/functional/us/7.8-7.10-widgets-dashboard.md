## 1. Périmètre à livrer

Trois cartes dashboard, chacune **gardée par son pilier** et avec un **état vide** propre :

### 7.8 — Record récent (`RecordRecentCard`)
- **Contenu** : le **dernier record battu**, tous piliers confondus (muscu OU course), avec sa **date**.
- **Données** : nouveau hook **`useMostRecentRecord()`** dans `dashboard-repository.ts` composant :
  - muscu : `SELECT ... FROM personal_records WHERE user_id=? AND deleted_at IS NULL ORDER BY achieved_at DESC LIMIT 1`
    (expose type `max_weight`/`estimated_1rm`/`best_volume`, valeur, nom d'exercice, `achieved_at`) ;
  - running : `useRunningRecords()` (ou requête dédiée `ORDER BY achieved_at DESC LIMIT 1`) → distance + temps + `achieved_at` ;
  - **fusion** → retourne le plus récent des deux (`{ pillar: 'strength'|'running', label, value, achievedAt } | null`).
- **Affichage** : badge pilier (Muscu / Course), libellé du record (ex. « Développé couché — 100 kg » ou
  « 5 km — 24:30 »), **date** (format court local JJ/MM/AAAA). Valeurs formatées via `useUnits`
  (poids `formatWeight`, allure/temps via helper existant).
- **État vide** : « Aucun record battu pour l'instant. »
- **Garde pilier** : affiché si `strength` **ou** `running` actif.
- **Lien** : « Voir les records → » (vers l'écran records correspondant — muscu Progression / running Historique).

### 7.9 — Volume muscu semaine (`MuscleVolumeCard`)
- **Contenu** : **barres de volume par groupe musculaire** pour la semaine en cours (lundi→dimanche, minuit local).
- **Données** : hook existant **`useMuscleVolumeThisWeek()`** (`records-repository.ts`) → `{ muscle, volume(kg) }[]`.
- **Affichage** : réutilise le composant existant **`MuscleVolumeBarChart`** (écran Progression). Volume en kg
  (le volume total est une charge cumulée, **non converti** en impérial au MVP — ou `useUnits` si trivial ; à trancher en revue).
- **État vide** : « Aucune séance cette semaine. »
- **Garde pilier** : `strength` actif.
- **Lien** : « Détail → » (vers Progression).

### 7.10 — Résumé running semaine (`RunningWeekCard`)
- **Contenu** : **distance + nombre de séances** de la semaine en cours, et **objectif de séances** si défini.
- **Données** : `useRunStats('week')` → `{ totalDistanceM, count }` ; **objectif séances** =
  `running_profiles.weeklyFrequency` (`running-profile-repository`, `number | null`).
- **Affichage** : distance (`useUnits().formatDistance(totalDistanceM/1000)`), et séances :
  - si `weeklyFrequency` défini → « **3 / 4 séances** » (+ éventuelle progression visuelle légère) ;
  - sinon → « **3 séances** » (sans objectif).
  - **Objectif de DISTANCE hebdo : différé** (aucune colonne stockée — hors périmètre, cf. §6).
- **État vide** : « Aucune course cette semaine. »
- **Garde pilier** : `running` actif.
- **Lien** : « Historique → » (vers `running-history`).

## 2. Règles / comportement

- **Semaine = lundi→dimanche, minuit local** (cohérent avec l'existant `startOfWeek`/`startOfWeekLocalUtc`).
- **Réactivité** : lecture `useQuery` (PowerSync) — les widgets se mettent à jour en temps réel après une séance/course/record.
- **Offline-first** : lecture locale seule ; aucune écriture ; fonctionne hors-ligne.
- **Ordre d'affichage** (Lot A, avant la personnalisation Lot B) : à la suite des widgets existants, ordre fixe
  proposé : Record récent, Volume muscu semaine, Résumé running semaine (à ajuster en revue/maquette).
- **i18n** : `home.record.*`, `home.volumeWeek.*`, `home.runningWeek.*` en FR **et** EN, à parité. Aucune chaîne en dur.
- **Unités** : distance via `useUnits` ; poids record via `useUnits`. Volume muscu = kg (arbitrage en revue).

## 3. Architecture

- **Hook** : `useMostRecentRecord()` (nouveau, `dashboard-repository.ts`) — composition owner-scopée des deux
  sources, tri par `achieved_at`, retour typé nullable. Hooks inconditionnels (React Compiler).
- **Composants** (nouveaux, `components/dashboard/`) : `RecordRecentCard`, `MuscleVolumeCard`, `RunningWeekCard`
  — chacun autonome, `DashboardCard` + contenu + état vide + lien. `MuscleVolumeCard` **réutilise**
  `MuscleVolumeBarChart`.
- **Intégration** : `(tabs)/index.tsx` — 3 rendus conditionnels supplémentaires (gardes piliers ci-dessus).
- **i18n** : ajout des 3 sous-arbres FR/EN.
- **Aucune** migration, sync rule, dépendance native. **Rebuild non requis** (JS pur ; couvert par un build ultérieur).
