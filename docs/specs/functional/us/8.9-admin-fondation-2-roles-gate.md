## 2. Modèle de données (migration `20260713xxxxxx_admin_user_roles.sql`)

- **Enum** `public.admin_role` = `('super_admin','content_editor','moderator')` (ou `text` + `check`).
- **Table** `public.user_roles` :
  `id uuid pk default gen_random_uuid()`, `user_id uuid not null references auth.users(id) on delete cascade`,
  `role admin_role not null`, `created_at timestamptz default now()`, `updated_at timestamptz default now()`,
  `deleted_at timestamptz`, **`unique(user_id, role)`** (partiel sur `deleted_at is null` si supporté, sinon simple).
  Trigger `set_updated_at`.
- **Fonctions `SECURITY DEFINER`** (contournent la RLS → évitent la récursion des policies sur `user_roles`) :
  - `public.is_admin()` → `bool` : l'utilisateur courant (`auth.uid()`) a ≥ 1 rôle non supprimé.
  - `public.is_super_admin()` → `bool` : a le rôle `super_admin` non supprimé.
  (`search_path` figé, `stable`.)
- **RLS** sur `user_roles` (enable) :
  - **select** : `user_id = auth.uid() OR public.is_super_admin()` (chacun voit ses rôles ; le super_admin voit tout).
  - **insert / update / delete** : `public.is_super_admin()` (seul un super_admin attribue/révoque ; les révocations
    = soft-delete via update `deleted_at`).
- **Pas** d'ajout à la publication PowerSync (table admin/web uniquement).

## 3. Bootstrap (1ᵉʳ super_admin)

```sql
insert into public.user_roles (user_id, role)
select id, 'super_admin' from auth.users where email = 'ton-email@exemple.fr';
```
(À exécuter une fois, après la migration. Ensuite le super_admin peut attribuer les autres rôles via l'UI.)

## 4. Comportement — gate & gestion (`apps/admin`)

### 4.1 Gate d'accès
- Après session établie (F1), l'admin **lit les rôles** de l'utilisateur courant :
  `supabase.from('user_roles').select('role').eq('user_id', <uid>)` (RLS autorise ses propres lignes).
- **`RequireAdmin`** (à l'intérieur de `RequireAuth`) :
  - chargement des rôles → spinner ;
  - ≥ 1 rôle → rend le shell ;
  - 0 rôle → écran **« Accès refusé »** (message FR + bouton **Déconnexion**) ;
  - **erreur de requête** (ex. table absente avant apply cloud, ou réseau) → traité comme **non-admin** (accès
    refusé), **jamais** de crash ; message générique.
- Expose `roles` + `isAdmin` + `isSuperAdmin` (hook `useRoles()` ou extension de `useAuth`).

### 4.2 Gestion minimale des rôles (super_admin only)
- Entrée de menu **« Rôles »** visible **uniquement si `isSuperAdmin`**.
- Écran : **liste** des attributions (`user_roles` non supprimés — le super_admin voit tout via RLS), colonnes
  `user_id`, `role`, date. **Attribuer** : champ `user_id` (UUID) + sélID de rôle → insert (gère le conflit
  `unique(user_id, role)` / réactivation si soft-deleted). **Révoquer** : bouton → confirmation → soft-delete.
- Message d'aide : « Copie l'UUID de l'utilisateur depuis le dashboard Supabase (Auth → Users). » (lookup e-mail = ultérieur.)
- Erreurs Supabase surfacées (FR) ; pas de crash.

## 5. Sécurité
- **RLS = frontière** : même si un non-admin ouvre l'app, il n'a **aucun rôle** → gate refuse ; et il ne peut ni
  lire les rôles des autres, ni s'auto-attribuer un rôle (insert refusé sauf super_admin).
- **Clé anon uniquement** (jamais `service_role`). Les fonctions `SECURITY DEFINER` sont limitées (lecture de
  `user_roles`, `search_path` figé).
- Le gate client est **du confort** ; la vraie protection des données = RLS côté serveur (un non-admin ne peut rien
  faire même en contournant l'UI).
