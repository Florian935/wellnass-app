# US 9.10 — Analytics produit first-party (événements anonymisés)

> Capter des **événements d'usage anonymisés** dans **notre propre base Supabase** (first-party), en
> **offline-first via PowerSync**, pour mesurer l'usage des testeurs pendant la bêta (activation, engagement,
> adoption) — sans jamais transmettre de donnée de santé/PII. Roadmap [9.10](../../../roadmap/roadmap.md)
> (V0.8, avant la bêta). Branche : `feature/9.10-analytics` · Date : 24/07/2026 ·
> **Statut : à valider (pas de code avant validation Florian/Damien).**
> **1 migration** (table + colonne consentement + RLS) ; aucun service tiers, aucune nouvelle infra.

## 0. Contexte

Aucune brique analytics n'existe. Avant d'ouvrir la bêta (Play interne), il faut pouvoir mesurer **comment les
testeurs utilisent l'app** (sinon aucune donnée). L'objectif long terme (roadmap) est aussi d'**alimenter la
décision gamification V3/V4** via des signaux de rétention.

Décisions de cadrage (brainstorming Florian, 24/07/2026) :
- **Stockage = table Supabase** (`analytics_events`) — vrai « first-party » : les données restent **dans notre
  base**, zéro nouvelle infra (cohérent « pas de Docker, dev sur cloud »), offline-first natif via PowerSync.
  Les tableaux de bord (funnels, rétention) viendront plus tard via un outil BI branché sur Supabase — **hors
  périmètre**.
- **Périmètre d'événements = socle (activation + engagement + actions cœur) + adoption de fonctions.**
- **Consentement = opt-out** : réglage « Statistiques d'usage » **activé par défaut**, coupable en un tap ;
  mention dans la politique de confidentialité. Base légale = intérêt légitime (analytics first-party non
  sensible). `track()` **respecte** le réglage (no-op si OFF).
- **Identifiant = `user_id`** (pseudonyme) : RLS naturelle + **purge en cascade** à la suppression de compte
  (cohérent CONF-02). Anonymat garanti autrement : **aucune PII ni donnée de santé** dans les propriétés.
- **Chemin d'écriture = via PowerSync** (comme toutes les tables) : offline-first gratuit. Accumulation locale
  négligeable à l'échelle bêta (purge locale = optimisation ultérieure, YAGNI).

Contexte technique (vérifié) :
- Schéma : toutes les tables suivent `id uuid pk` + `user_id uuid references auth.users(id) on delete cascade`
  + `created_at`/`updated_at`/`deleted_at`. `user_settings` a une ligne unique par `user_id`.
- Migrations via CLI (jamais de SQL collé) : `db:new` → écrire le SQL → `db:push` (cloud) → `db:types` → cocher
  dans [supabase/MIGRATIONS.md](../../../../supabase/MIGRATIONS.md).
- `expo-application` + `Platform` (déjà installés via US 1.22) fournissent version d'app + plateforme.

## 1. Périmètre à livrer

- **Migration** : table `analytics_events` (append-only) + RLS (insert/select propres) + colonne
  `user_settings.analytics_enabled` (boolean, défaut `true`).
- **PowerSync** : ajout de `analytics_events` au **schéma client** (`AppSchema`) + aux **sync rules** (bucket par
  `user_id`) ; mapping du champ `analytics_enabled` dans le repository `user_settings`.
- **Service `track(eventName, props?)`** (`apps/mobile/src/lib/analytics.ts`) : gating consentement (no-op si
  OFF), assainissement des propriétés (allowlist), écriture offline-first (PowerSync), **jamais bloquant**.
- **Helper pur** (assemblage de la ligne + assainissement des propriétés) — **testé**.
- **Réglage** « Statistiques d'usage » (opt-out) dans les Réglages + **mention politique de confidentialité**.
- **Instrumentation** des ~15 points d'événement (socle + adoption).
- **i18n FR/EN** (réglage + mention confidentialité). Aucune chaîne en dur.

**Hors périmètre (à ne pas implémenter ici) :**
- **Tableaux de bord / funnels / rétention** (via outil BI branché sur Supabase — ultérieur).
- **Crash / erreur reporting** (type Sentry) — autre brique.
- **Purge locale** des vieux événements (optimisation si le volume gêne un jour).
- **Analytics dans l'export CONF-01** (télémétrie dérivée, pas du contenu saisi) — évolution possible.
- **Contrôle de flux avancé** (batching serveur, échantillonnage) — au-delà du throttle simple d'`app_opened`.

## 2. Comportement attendu

### 2.1 Table `analytics_events`
- Colonnes : `id` (uuid, client), `user_id` (uuid, **FK `auth.users(id) on delete cascade`**), `event_name`
  (text), `properties` (jsonb, défaut `{}`), `app_version` (text), `platform` (text), `occurred_at`
  (timestamptz, UTC client), `created_at` (timestamptz, défaut `now()`).
- **Append-only** : aucune colonne `deleted_at`/`updated_at` (jamais édité ni soft-deleted).
- **RLS** activée : policy **insert** `with check (auth.uid() = user_id)` + policy **select**
  `using (auth.uid() = user_id)`. **Pas** de policy update/delete (le client n'édite/supprime jamais).
- **Purge** : la cascade FK supprime les événements à la suppression du compte (cohérent CONF-02).

### 2.2 Consentement (opt-out)
- Migration : `alter table user_settings add column analytics_enabled boolean not null default true;`.
- Mappé dans le repository `user_settings` (+ type partagé) et dans le **schéma client PowerSync**.
- Réglage **« Statistiques d'usage »** (section Confidentialité/Données des Réglages) : interrupteur ON par
  défaut, sous-titre explicatif (« Nous aide à améliorer l'app. Données anonymes, jamais tes données de
  santé. »). Bascule immédiate, synchronisée entre appareils.
- **Mention** ajoutée à `privacy.tsx` (politique de confidentialité) : analytics anonymisées first-party,
  désactivables dans les Réglages.

### 2.3 Service `track(eventName, props?)`
- **Gating** : lit `analytics_enabled` (réglages courants) ; si `false` (ou pas de session) → **no-op** (return).
- Construit la ligne : `id` (uuid client), `user_id` (session), `event_name`, `properties` **assainies**,
  `app_version` (`expo-application`), `platform` (`Platform.OS`), `occurred_at` (ISO UTC).
- **Assainissement (`sanitizeProps`)** : **allowlist stricte et figée** des clés autorisées — au lancement, la
  seule clé utilisée par le catalogue §2.4 est **`pillar`** (valeur ∈ `strength|running|nutrition`). L'allowlist
  est une constante extensible au fil des futurs événements. N'accepte que des **valeurs scalaires**
  (string/number/boolean) ; toute clé hors allowlist ou valeur non scalaire est **écartée** silencieusement.
  Garantit qu'aucune PII / donnée de santé / texte libre ne parte, même en cas d'appel erroné. Testable de façon
  déterministe (liste fermée).
- Écrit via repository PowerSync. **Ne jette jamais** (try/catch interne, `console.warn` en cas d'échec) — un
  échec analytics ne doit jamais casser un parcours ni bloquer l'UI. Fonctionne **hors-ligne**.

### 2.4 Catalogue d'événements (socle + adoption)
Convention : nom `snake_case`, propriétés minimales non identifiantes.
- **Cycle de vie / engagement** : `app_opened` (au passage au premier plan, **throttlé** ≥ 30 min pour éviter
  les rafales).
- **Activation / onboarding** : `onboarding_started`, `onboarding_completed`, `onboarding_skipped`,
  `pillar_activated` (`{ pillar }`).
- **Actions cœur** : `workout_started`, `workout_completed`, `run_started`, `run_completed`, `food_logged`.
- **Adoption de fonctions** : `stats_viewed` (`{ pillar }`), `dashboard_customized`, `data_exported`,
  `help_opened`, `bug_reported`.
> La liste exacte des points d'ancrage est arrêtée au plan ; ne pas instrumenter au-delà de ce catalogue (YAGNI).

## 3. Architecture

- **Migration** (`supabase/migrations/<horodaté>_analytics_events.sql`) : `create table analytics_events …` +
  `enable row level security` + policies insert/select + `alter table user_settings add column
  analytics_enabled …`. Poussée via `db:push`, types régénérés (`db:types`), cochée dans `MIGRATIONS.md`.
- **PowerSync** : `analytics_events` ajouté au **schéma client** (`AppSchema`, colonnes ci-dessus) et aux **sync
  rules** (bucket data `select * from analytics_events where user_id = token_parameters.user_id`). ⚠️ La mise à
  jour des **sync rules** sur l'instance PowerSync est une **étape de déploiement** (comme l'activation pg_cron
  de CONF-02) — à appliquer avant la recette.
- **`apps/mobile/src/lib/analytics.ts`** : `sanitizeProps` (pur, testé), `buildEventRow` (pur, testé),
  `track(eventName, props?)` (gating + I/O PowerSync, non bloquant). Réutilise `expo-application`/`Platform`.
- **Repository** : **insert dédié** append-only pour `analytics_events` — **ne PAS réutiliser** les helpers qui
  injectent `updated_at`/`deleted_at` (la table n'a que `created_at`) ; la ligne vient de `buildEventRow`, avec
  `properties` **sérialisé en TEXT** côté SQLite (`JSON.stringify`, comme `active_pillars`/`notifications`).
  Lecture/mapping de `analytics_enabled` dans le repository `user_settings` (+ `updateSettings`), via un
  **accesseur** permettant à `track()` de lire le consentement **hors contexte React**.
- **Instrumentation** : appels `track(...)` aux points du §2.4 (dans les stores/écrans concernés).
- **Type partagé** (`@wellness/shared`) : ajout de `analyticsEnabled` au type `UserSettings` + schéma Zod si présent.

## 4. i18n (FR + EN)

Aucune chaîne en dur ; parité stricte. Clés indicatives : `settings.analytics.{title, subtitle}` ;

Exemples FR→EN : « Statistiques d'usage » → « Usage statistics » ; « Nous aide à améliorer l'app. Données

## 5. Offline & performance

- `track()` marche **hors-ligne** (écriture locale → sync PowerSync à la reconnexion).
- Événements = petites lignes texte ; volume bêta négligeable. `app_opened` throttlé pour éviter les rafales.

## 6. Sécurité & RGPD

- **Pseudonyme, non sensible** : `user_id` + événements comportementaux ; **jamais** de donnée de santé, PII ou
  texte libre (garanti par l'allowlist `sanitizeProps`).
- **Opt-out respecté** : aucun `track()` si `analytics_enabled = false`.
- **Purge** automatique à la suppression du compte (cascade FK).
- **Transparence** : mention dans la politique de confidentialité.
- RLS : chaque utilisateur n'insère/ne lit que ses propres événements.

## 7. Cas limites

- **Consentement OFF** → `track()` est un no-op complet (aucune écriture locale).
- **Pas de session / user_id absent** → no-op (pas d'événement orphelin).
- **Propriété non autorisée** passée à `track()` → écartée par `sanitizeProps` (l'événement part sans elle).
- **Échec d'écriture** → `console.warn`, aucun crash, parcours utilisateur intact.
- **Hors-ligne** → événement écrit localement, synchronisé plus tard.
- **`app_opened` rapproché** (retour premier plan < 30 min) → non renvoyé (throttle).

## 9. Critères d'acceptation (recette)

1. **Événement écrit** : déclencher une action instrumentée (ex. terminer une séance) → une ligne
   `analytics_events` apparaît (vérifiable côté Supabase) avec `event_name`, `user_id`, `occurred_at`,
   `app_version`, `platform` corrects.
2. **Opt-out respecté** : désactiver « Statistiques d'usage » → refaire l'action → **aucune** nouvelle ligne.
   Réactiver → les événements repartent.
3. **Anti-PII** : les `properties` ne contiennent que des clés autorisées (ex. `pillar`), **jamais** de donnée
   de santé/perso.
4. **Offline** : en mode avion, l'action instrumentée crée l'événement localement, synchronisé à la reconnexion.
5. **Purge compte** : après suppression de compte (CONF-02), les `analytics_events` du compte sont supprimés.
6. **Catalogue** : les ~15 événements du §2.4 se déclenchent aux bons moments (échantillon vérifié).
7. **i18n** : réglage + mention confidentialité traduits en anglais.
