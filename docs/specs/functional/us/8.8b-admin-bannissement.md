# US 8.8b — Bannissement des utilisateurs (back-office)

_Spec fonctionnelle. Statut : en validation (brainstorming Florian, 16/07/2026). Branche :
`feature/8.8b-admin-bannissement` (depuis `dev`). Seconde moitié de l'US 8.8 (roadmap V0.7) ; complète
la consultation **8.8a** (déjà livrée)._

## 1. Contexte & objectif

8.8a a livré la **consultation** (vue `admin_users`, fonction `can_manage_users()`, écrans liste/fiche
lecture seule). 8.8b ajoute l'**action de modération** : **bannir / débannir** un compte depuis la
fiche, réservée aux rôles habilités.

**Contrainte structurante (rappel 8.8a)** : l'admin n'a que la **clé anon** (jamais `service_role`).
Or bannir = écrire `auth.users.banned_until`, impossible en anon. Le mécanisme retenu (décision
Florian, 16/07/2026) : des **fonctions RPC SQL `SECURITY DEFINER`** (via migration), qui s'exécutent
avec les droits de leur propriétaire (rôle de migration = `postgres`) et peuvent donc écrire dans le
schéma `auth`, tout en vérifiant l'habilitation de l'appelant en interne.

**Décisions de cadrage (Florian, 16/07/2026)** :
- **Ban permanent** jusqu'à débannissement manuel (`banned_until = 'infinity'`). Pas de durée temporaire.
- **Garde-fous** : on ne peut bannir **ni soi-même, ni un compte doté d'un rôle admin** (super_admin /
  content_editor / moderator).
- **Motif obligatoire** à chaque bannissement ; **historique conservé** (table `user_bans` append-only).
- **Coupure au prochain refresh** (~1 h max) : `banned_until` bloque le renouvellement du token → l'accès
  (app + synchro PowerSync) se coupe au prochain refresh. Pas de révocation immédiate des sessions.

## 2. Périmètre

- **Inclus** :
  - Table **`user_bans`** (append-only : historique des bans/débannissements + motif).
  - RPC **`public.ban_user(target_user_id uuid, reason text)`** et **`public.unban_user(target_user_id uuid)`**
    (`SECURITY DEFINER`), avec toutes les vérifications (habilitation, garde-fous, motif).
  - Actions **Bannir / Débannir** sur la fiche `/users/:id` (8.8a) : bouton + saisie du motif +
    confirmation ; affichage du **motif courant** si banni ; **historique** des bans sous la fiche.
  - Couche data `apps/admin/src/data/users.ts` étendue : `banUser`, `unbanUser`, `listUserBans`.
  - `logAudit('user.ban' | 'user.unban')` (journal 8.10, best-effort) après succès. ⚠️ **Ces deux
    actions n'existent pas encore** : l'audit est une **union fermée**. Il faut **étendre**
    `AUDIT_ACTIONS` (+`user.ban`, +`user.unban`) dans [packages/shared/src/audit.ts](../../../packages/shared/src/audit.ts)
    (type + `z.enum`) **et** ajouter les 2 libellés correspondants dans `fr.audit.action` de l'i18n
    admin (sinon `AuditScreen` — qui fait `fr.audit.action[a]` sur toute l'union — casse le typecheck).
  - i18n admin FR.
  - `npm run db:types` après migration (table `user_bans` + RPC `ban_user`/`unban_user` + colonne
    `is_admin` de la vue apparaissent dans les types).
- **Exclu (YAGNI)** :
  - **Durée temporaire** de ban (expiration auto) — permanent + débannir manuel seulement.
  - **Révocation immédiate** des sessions actives (`auth.sessions`) — on accepte la latence ~1 h.
  - Notification à l'utilisateur banni, motifs prédéfinis, appel/contestation — hors périmètre.
  - Édition d'un motif passé (l'historique est **immuable**).
- **Maquette** : écartée (réutilisation des composants/style admin existants : boutons, `window.prompt`
  ou petit modal de saisie, panels de la fiche 8.8a). À confirmer à la validation.

## 3. Modèle de données

### 3.1 Table `public.user_bans` (append-only, historique)

| Colonne | Type | Note |
|---|---|---|
| `id` | uuid PK (`gen_random_uuid()`) | |
| `target_user_id` | uuid `references auth.users(id) on delete cascade` | compte concerné |
| `action` | text `check (action in ('ban','unban'))` | type d'événement |
| `reason` | text | **requis** pour `ban` (contrainte : `action='unban' or (reason is not null and length(trim(reason)) > 0)`) |
| `acted_by` | uuid `references auth.users(id)` | admin ayant agi (`auth.uid()` au moment de l'appel) |
| `created_at` | timestamptz not null default now() | |

- **Append-only** : chaque ban/débannissement = une ligne. Pas de `deleted_at`, pas d'UPDATE (immuable).
- **Index** : `(target_user_id, created_at desc)` (afficher l'historique + retrouver le dernier événement).
- **RLS** : `enable row level security` ; **une seule policy** `select using (public.can_manage_users())`.
  **Aucune** policy `insert`/`update`/`delete` → le client (clé anon) ne peut **jamais** écrire en
  direct ; seules les RPC `SECURITY DEFINER` insèrent (elles contournent la RLS en tant que propriétaire).
- **Hors PowerSync** (table web-admin) — pas d'ajout à la publication `powersync`.

### 3.2 RPC `public.ban_user(target_user_id uuid, reason text)`
`SECURITY DEFINER`, `language plpgsql`, `set search_path = public`, propriétaire = rôle de migration
(`postgres`, qui a les droits sur `auth.users`). `GRANT EXECUTE ... TO authenticated`. Corps :

1. **Habilitation** : `if not public.can_manage_users() then raise exception ...` (super_admin/moderator).
2. **Motif** : `if reason is null or length(trim(reason)) = 0 then raise exception ...`.
3. **Garde-fou anti-auto-ban** : `if target_user_id = auth.uid() then raise exception ...`.
4. **Garde-fou anti-ban-admin** : `if exists (select 1 from public.user_roles where user_id =
   target_user_id and deleted_at is null) then raise exception ...`.
5. `update auth.users set banned_until = 'infinity' where id = target_user_id;`
6. `insert into public.user_bans(target_user_id, action, reason, acted_by)
   values (target_user_id, 'ban', trim(reason), auth.uid());`

> Atomique (une transaction de fonction) : si une vérif échoue, aucun effet. Les `raise exception`
> remontent à supabase-js comme une erreur (à mapper en message FR côté UI).
>
> **Privilèges** : `GRANT EXECUTE ... TO authenticated` **et** `REVOKE EXECUTE ON FUNCTION
> public.ban_user(uuid, text) FROM public, anon;` (défense en profondeur, cohérent avec le `REVOKE …
> FROM anon` de la vue 8.8a — `CREATE FUNCTION` accorde `EXECUTE` à `PUBLIC` par défaut ; on le retire).
> Idem pour `unban_user`.

### 3.3 RPC `public.unban_user(target_user_id uuid)`
Même enveloppe. Corps :
1. **Habilitation** : `can_manage_users()` sinon `raise`.
2. `update auth.users set banned_until = null where id = target_user_id;`
3. `insert into public.user_bans(target_user_id, action, acted_by)
   values (target_user_id, 'unban', auth.uid());` (`reason` null — autorisé par la contrainte).

> **Débannissement non gardé** par l'anti-admin (un admin n'est de toute façon jamais banni) ni par
> l'anti-soi-même (sans objet). Seule l'habilitation est requise.

> ⚠️ **Checkpoint migration 🔴** (dev sur cloud, pas de Docker) : `db:new` → SQL → `db:push:dry` →
> `db:push` → `db:types` → cocher [MIGRATIONS.md](../../../supabase/MIGRATIONS.md). **Pas de sync rule.**
> Vérifs après apply :
> 1. **Test de privilège isolé (AVANT d'écrire les écrans)** : dans le SQL Editor connecté en `postgres`,
>    `update auth.users set banned_until='infinity' where id='<uuid test>';`. Si « permission denied for
>    table users » → les RPC échoueront en prod, à traiter avant d'aller plus loin. _(Sur le cloud actuel,
>    `postgres` a les droits sur le schéma `auth` ; ce test le confirme sans risque.)_
> 2. **`banned_until='infinity'` refuse-t-il bien le refresh côté GoTrue ?** Risque assumé/à valider :
>    le parsing Go de `infinity` peut poser problème selon la version. Si un compte à `'infinity'`
>    n'est **pas** refusé au refresh → repli **sentinelle date lointaine** `'9999-12-31T00:00:00Z'`
>    (même sémantique « ban permanent », `is_banned` inchangé). Décider au checkpoint.
> 3. Fonctionnel : `super_admin` bannit un compte **normal** (→ Banni) ; `ban_user` sur soi-même ou sur
>    un compte admin **échoue** (exception) ; `unban_user` repasse Actif ; `user_bans` s'incrémente.

## 4. Écran — fiche `/users/:id` (complète 8.8a)

- **Section « Modération »** (nouvelle), visible pour `can_manage_users()` :
  - Cible **non bannie** (`is_banned = false`) : bouton **« Bannir »** → saisie du **motif**
    (obligatoire ; `window.prompt` ou petit champ inline) → **confirmation** → `banUser`. Si motif vide
    → pas d'appel (bouton/validation inactifs).
  - Cible **bannie** (`is_banned = true`) : badge « Banni » + **motif courant** (dernier `ban`) + bouton
    **« Débannir »** → confirmation → `unbanUser`.
  - **Garde-fous UI** (miroir du serveur) : la section d'action est **masquée** si la cible **est un
    admin** (a un rôle actif) **ou** **est soi-même** (`user.id === session.user.id`). Un message neutre
    peut l'indiquer (« Ce compte ne peut pas être banni »).
- **Historique des bans** : liste sobre sous la fiche (date JJ/MM/AAAA · action Banni/Débanni · motif ·
  acteur). Vide → « Aucun événement ». ⚠️ `user_bans.acted_by` n'est qu'un **UUID** ; le client anon ne
  lit pas `auth.users` → pour afficher l'e-mail de l'acteur, **mapper l'UUID via `admin_users`** (déjà
  lisible par `can_manage_users()`) : soit un petit lookup `getUser(acted_by)`, soit afficher l'UUID en
  repli si non résolu. (Pas de jointure `auth.users` directe possible.)
- Après ban/débannissement réussi → **recharger** la fiche (statut + historique à jour).
- **Erreur RPC** (ex. garde-fou déclenché côté serveur) → message FR non bloquant (role="alert").

> **Détection « cible est un admin »** : le plus simple est d'exposer l'info au client. Deux options à
> trancher au plan : (a) une petite requête `user_roles` (lisible par super_admin via RLS existante —
> **mais un moderator ne peut pas lire `user_roles`**, donc KO pour lui) ; (b) **ajouter une colonne
> `is_admin` calculée à la vue `admin_users`** (`exists(select 1 from user_roles …)`) — lisible par
> tout `can_manage_users()` (la vue tourne en droits propriétaire → contourne la RLS de `user_roles`,
> qu'un `moderator` ne peut pas lire directement). **Option (b) retenue** (une seule source). ⚠️ Elle
> implique de **modifier la vue** dans la même migration 8.8b : `create or replace view
> public.admin_users …` en **conservant les colonnes existantes dans le même ordre** et en **ajoutant
> `is_admin` EN DERNIER** (après `language`) — Postgres interdit de supprimer/réordonner/renommer les
> colonnes d'une vue via `create or replace`, on ne peut qu'ajouter à la fin.

## 5. Couche data — `apps/admin/src/data/users.ts` (étendue)

- `banUser(targetUserId, reason)` → `supabase.rpc('ban_user', { target_user_id, reason })` ; renvoie
  `{ error }`. Après succès : `logAudit({ action: 'user.ban', targetTable: 'auth.users',
  targetId: targetUserId, details: { reason } })` (best-effort).
- `unbanUser(targetUserId)` → `supabase.rpc('unban_user', { target_user_id })` ; après succès
  `logAudit({ action: 'user.unban', ... })`.
- `listUserBans(targetUserId)` → `{ rows, error }` (`from('user_bans').select('*').eq('target_user_id',
  …).order('created_at', { ascending: false })`). Type `UserBanRow = Database['public']['Tables']['user_bans']['Row']`.
- `AdminUserRow` gagne la colonne `is_admin` (via la vue modifiée) → utilisée par le garde-fou UI.

> ⚠️ **Ordre de build** (comme en 8.8a) : `data/users.ts` dépend de `Database['public']['Tables']['user_bans']['Row']`
> et des RPC typées → **ne pas écrire/committer le code data avant** le `db:push` + `db:types` du
> checkpoint, sinon `typecheck` casse.

## 7. Cas limites & sécurité

- **Auto-ban** : bloqué serveur (raise) **et** UI (section masquée pour soi-même).
- **Ban d'un admin** : bloqué serveur (raise) **et** UI (section masquée si `is_admin`).
- **Motif vide/espaces** : refusé (UI + contrainte SQL + garde RPC).
- **Double ban** (déjà banni) : `banned_until` re-posé à `'infinity'` (idempotent) + nouvelle ligne
  d'historique — acceptable ; l'UI ne propose « Bannir » que si `!is_banned`.
- **Débannissement d'un compte non banni** : `banned_until = null` (no-op effectif) + ligne `unban` —
  l'UI ne propose « Débannir » que si `is_banned`.
- **`content_editor`** : `can_manage_users()` renvoie `false` → RPC refusée **et** section absente
  (il n'accède déjà pas à `/users`, cf. 8.8a).
- **Latence** : accès effectivement coupé au **prochain refresh du token** (~1 h max) — documenté,
  assumé (pas de révocation de session en V1).
- **Sécurité RPC** : `SECURITY DEFINER` + `search_path=public` figé (anti-injection) ; toutes les
  vérifs **dans** la fonction (ne pas se fier au client) ; `GRANT EXECUTE` à `authenticated` mais la
  première instruction est le contrôle `can_manage_users()`.
