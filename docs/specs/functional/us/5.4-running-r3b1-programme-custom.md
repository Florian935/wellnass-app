# US Running R3b-i — Programme de course custom

> Premier incrément de **R3b** (programmes de course), découpé en R3b-i (programme custom) et
> R3b-ii (bibliothèque + filtres + seed). Réutilise l'infra **programmes muscu** (déjà pilier-aware).
> Réf. fonctionnelle : [running.md](../running.md) §3. S'appuie sur R3a (types de séance + allures).
> Branche : `feature/running-r3b1-programme-custom` · Date : 11/07/2026 ·
> **Statut : à valider (pas de code avant validation).**

## 0. Contexte

L'infra **programmes muscu** est **pilier-aware et réutilisable** :
- Table `programs` : colonne `pillar text check (pillar in ('strength','running'))`, + `owner_id` (NULL = bibliothèque, non-null = custom user), `status`, `is_active`, `level check (beginner/intermediate/advanced)`, `goal` (texte libre), `duration_weeks`.
- Table `sessions` : générique (`program_id`, `owner_id`, `order_index`, `name`).
- Table `program_translations` : bilingue FR/EN.
- Repository `program-repository.ts` **déjà pilier-paramétré** : `createProgram({pillar})`, `useActiveProgram(pillar)`, `activateProgram` (un actif par pilier), `duplicateProgram`, `useMyPrograms`, `addSession`.
- Seul le **contenu de séance** diffère : muscu = `exercise_plans` ; running = **type + cible (distance/durée)**.

R3b-i ajoute le **contenu de séance running** et l'**écran de création/édition** d'un programme de course custom.

## 1. Périmètre à livrer

Créer / éditer / activer / dupliquer un **programme de course custom** (`pillar='running'`) :
- **Métadonnées** : nom + **résumé** (bilingues via `program_translations.name`/`summary`), **objectif** (`RUNNER_OBJECTIVES` stocké dans `programs.goal`), **niveau** (`programs.level` = beginner/intermediate/advanced, libellés FR/EN), **durée** (`duration_weeks`). *(La « fréquence hebdo » de running.md §3.1 n'est **pas** un champ stocké au MVP — implicite via le nombre de séances ; un champ dédié est différé.)*
- **Séances ordonnées** (`sessions`) : chaque séance = un **type** (`SESSION_TYPES` hors `course_libre`) + une **cible** = **distance (km)** *ou* **durée (min)** + un nom optionnel. L'**allure cible** de la séance est **affichée** (dérivée du type + profil coureur R3a, `sessionTargetPace`), non stockée.
- **Activation** : un seul programme running actif à la fois (réutilise `activateProgram`, déjà un-actif-par-pilier).
- **Duplication** : réutilise `duplicateProgram` (copie header + traductions + séances + contenu running).

**Hors périmètre :**
- **Structure détaillée / blocs d'intervalles** (fractionné « 6×400 m récup 1:30 ») → **différée** (incrément ultérieur). Au MVP, une séance fractionné = type `fractionne` + cible + allure affichée, sans blocs.
- **Bibliothèque + filtres + programmes seedés** → **R3b-ii**.
- **Planning calendrier / coordination muscu-running / séance manquée** → **R3c**.
- **Démarrer une course DEPUIS une séance de programme** (lien tracker) → différé (R3c/ultérieur) ; R1 reste « course libre ».
- Progression automatique de volume (running.md §3.3 pt 4) → différée.

## 2. Comportement attendu

1. **Liste des programmes running** : dans l'écran programmes (filtré `pillar='running'`), section « Mes programmes » (custom). Bouton « Créer un programme de course ».
2. **Création / édition** (écran builder, patron muscu `programs/edit.tsx`) : saisir nom + objectif + niveau + durée ; ajouter des séances ; pour chaque séance, choisir le **type** et saisir la **cible** (distance en km **ou** durée en min — l'unité de distance suit `useUnits`). L'**allure cible** s'affiche sous la séance (plage `sessionTargetPace(type, refPaceProfil)` via `useUnits`, ou invite « définis ton allure de réf » si pas de profil).
3. **Détail programme** (patron `programs/[id].tsx`) : métadonnées + liste des séances (type, cible, allure) + **Activer** / **Dupliquer**.
4. **Réactif** (`useQuery`) ; **offline-first**.

## 3. Règles métier

- **Réutilisation** : `programs` (`pillar='running'`), `sessions`, `program_translations` — **pas de nouvelles tables** ; on **étend `sessions`** de colonnes de contenu running **nullables** (les séances muscu les laissent nulles).
- **Niveau** : running réutilise l'échelle `programs.level` = `beginner`/`intermediate`/`advanced` (i18n : « Débutant / Régulier / Confirmé »). Le niveau du **profil** coureur (R3a, `debutant/regulier/confirme`) reste distinct ; mapping 1:1 pour le filtrage **en R3b-ii**.
- **Objectif** : stocké dans `programs.goal` (valeur `RUNNER_OBJECTIVES`).
- **Cible de séance** : `target_distance_m` (entier, mètres) **ou** `target_duration_seconds` (entier) — **au moins l'un des deux pour une séance running**. Enforcé (a) côté app/Zod (l'éditeur exige une cible) **et** (b) par une **check constraint SQL conditionnelle** : `check (session_type is null or target_distance_m is not null or target_duration_seconds is not null)` — ne s'applique qu'aux séances running (`session_type` non nul) et **laisse passer les séances muscu** (`session_type` nul, deux cibles nulles). Distance saisie en km (via `useUnits`, stockée en mètres SI).
- **Allure** : jamais stockée (dérivée à l'affichage du type + profil ; `sessionTargetPace`). `course_libre` exclu des types de séance de programme.
- **Un seul actif par pilier** (déjà garanti par `activateProgram`).

## 4. Architecture

- **Migration (🔴 cloud)** : `alter table public.sessions add column session_type text check (session_type in ('endurance','fractionne','sortie_longue','recuperation'))`, `add column target_distance_m integer`, `add column target_duration_seconds integer` (tous **nullables**, additif/rétrocompatible) + la **check constraint conditionnelle de cible** (cf. §3). La check `session_type` est **volontairement restrictive** (4 types de programme ; `course_libre` et types futurs exclus — à étendre par une migration si `SESSION_TYPES` évolue). Aucune nouvelle table, aucune sync rule à changer (`sessions` déjà dans `user_data` + `shared_content`). Timestamp **> `20260712090000`** (à coordonner avec Damien).
- **Schéma PowerSync local** (`schema.ts`) : ajouter `session_type`/`target_distance_m`/`target_duration_seconds` à la déclaration `sessions` (`column.text`/`column.integer`).
- **`@wellness/shared`** : schéma Zod du contenu de séance running si utile (`runningSessionContentSchema`) ; réutilise `SESSION_TYPES`/`RUNNER_OBJECTIVES` + `sessionTargetPace`.
- **Repository** : réutiliser `createProgram`/`addSession`/`activateProgram`/`useMyPrograms`. **`duplicateProgram`** : ⚠️ **vérifier et étendre** pour qu'il recopie aussi les nouvelles colonnes `session_type`/`target_distance_m`/`target_duration_seconds` (sinon les séances dupliquées arrivent **vides de contenu running**). **Ajouter** `updateRunningSession(sessionId, { sessionType?, targetDistanceM?, targetDurationSeconds?, name? })` (patch `sessions`). **Détail** : **préférer étendre `SessionDetail`** avec `sessionType/targetDistanceM/targetDurationSeconds` **nullables** (muscu les ignore) — évite de dupliquer la logique de cache/subscription PowerSync d'un hook séparé ; ne créer un hook running dédié que si le type partagé devient intenable. Choix confirmé au **plan**.
- **Écrans** : réutiliser/étendre `apps/mobile/src/app/programs/` (liste filtrée par pilier, détail, éditeur). Un **éditeur de séance running** (type picker + cible distance/durée + allure affichée) remplace `ExercisePlanEditor` quand `pillar='running'`. Entrée « Créer un programme de course » (dans l'onglet Course / programmes, si pilier running actif).
- **i18n** FR+EN : libellés niveau, objectif (réutiliser `running.objective.*` de R3a), types (`running.sessionType.*` de R3a), champs cible (distance/durée), actions.
