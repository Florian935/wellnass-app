# US 4.7b — Détection anticipée des jours d'entraînement (nutrition)

> Complément de 4.7 (bonus calorique des jours de séance). Aujourd'hui la détection est **rétroactive**
> (séance muscu/course **terminée** ce jour-là). Maintenant qu'un **planning daté** existe
> (`planned_sessions`, US 3.9), un jour avec une séance **planifiée** doit compter comme jour
> d'entraînement **par anticipation**. Réf. : [metriques-succes / musculation §2.4 / nutrition 4.7].
> Branche : `feature/nutrition-4.7-anticipee` · Date : 12/07/2026 · **Statut : à valider (pas de code avant validation).**

## 0. Contexte

- `useIsTrainingDay(dayKey)` (`dashboard-repository.ts`) = « au moins une séance muscu **terminée** OU une
  course **terminée** ce jour-là », composé de `useWorkoutHistory` + `useRunHistory` (timestamps `finishedAt`
  UTC → jour local via `localDayKey`). **Rétroactif** (« faute de planning muscu daté » — commentaire du code).
- Consommateurs : `useNutritionSummary` (dashboard, **aujourd'hui**) et le **journal** `(tabs)/nutrition.tsx`
  (jour **affiché**, navigable passé/futur via `setDay(addDays(day, ±1))`) — appliquent le bonus calorique
  (`effectiveTarget = trainingDayCalories(target, bonus)`) + badge « +X kcal · jour de séance ».
- US 3.9 a livré `planned_sessions` (générique, pilier-agnostique) + le repo `planned-session-repository`.

## 1. Périmètre à livrer

Étendre `useIsTrainingDay(dayKey)` pour qu'une **séance planifiée** ce jour-là compte comme jour
d'entraînement **par anticipation** (sans attendre qu'elle soit faite), et donc déclenche le **bonus calorique**
sur le dashboard (aujourd'hui) et le journal (jour affiché). **Aucune migration, aucun cloud, 100 % JS.**

**Hors périmètre :**
- Modifier le calcul du bonus lui-même (montant, ventilation macros) — inchangé (4.7).
- Distinguer visuellement « prévu » vs « fait » dans le badge — **différé** (même badge au MVP).
- Toucher au **streak** (`useStreakData`) — reste sur les séances **terminées** uniquement (le streak récompense
  le fait accompli, pas l'intention). **Ne pas** anticiper le streak.
- Progression auto de volume, coordination avancée.

## 2. Comportement attendu

Un jour `dayKey` est un **jour d'entraînement** si **l'une** des conditions est vraie :
1. **(rétroactif — tout jour, inchangé)** une séance muscu **terminée** OU une course **terminée** ce jour-là ;
2. **(anticipé — aujourd'hui + futur uniquement)** il existe une **séance planifiée** ce jour-là
   (`planned_sessions`, statut `planned` **ou** `done`), **et** `dayKey >= aujourd'hui` (`todayKey`).

Conséquences :
- **Jour passé** : comportement **inchangé** (rétroactif seul). Une séance passée **planifiée mais non faite
  (manquée)** ne donne **pas** rétroactivement le bonus.
- **Aujourd'hui / futur** : une séance planifiée déclenche le bonus (anticipation — l'utilisateur peut ajuster
  son alimentation à l'avance).
- Le **badge** et le montant du bonus sont **identiques** que la détection soit rétroactive ou anticipée.
- `skipped` **exclu** (l'utilisateur a renoncé à cette séance).

## 3. Règles métier

- **Fenêtre d'anticipation** : uniquement `dayKey >= todayKey` (date locale `localDayKey(new Date())`). Le passé
  n'est jamais anticipé (cohérence : on ne « récrit » pas l'historique nutritionnel).
- **Statuts planifiés comptés** : `planned` + `done` ; `skipped` exclu.
- **Union**, pas de double comptage : un jour reste un simple booléen « jour d'entraînement » ; peu importe qu'il
  soit détecté par 1, 2 ou 3 sources.
- **Streak inchangé** : la détection anticipée n'affecte **que** `useIsTrainingDay`/le bonus nutrition, pas le
  streak (qui garde sa logique « séance terminée »).
- **Offline-first** : lecture locale réactive ; aucune écriture ; aucun schéma changé.

## 4. Architecture

- **Repo** (`planned-session-repository.ts`) : nouveau hook réactif léger
  **`useHasPlannedSession(dayKey)`** → `{ hasPlanned: boolean; isLoading }`, requête bornée :
  `SELECT 1 FROM planned_sessions WHERE owner_id = ? AND scheduled_date = ? AND status IN ('planned','done') AND deleted_at IS NULL LIMIT 1`
  (owner-scopé, params liés ; `useQuery` réactif ; `isLoading` = résolution locale, offline-first).
- **Logique pure testable** (`@wellness/shared`) : `isTrainingDay({ retroactiveDone, hasPlanned, dayKey, todayKey })`
  → `retroactiveDone || (hasPlanned && dayKey >= todayKey)` (comparaison de chaînes `AAAA-MM-JJ`,
  lexicographique = chronologique). Pure, testée (passé sans anticipation, aujourd'hui/futur avec, statut, égalité).
- **`useIsTrainingDay(dayKey)`** (`dashboard-repository.ts`) : compose l'existant (`useWorkoutHistory` +
  `useRunHistory` → `retroactiveDone`) **+** `useHasPlannedSession(dayKey)` → `hasPlanned`, et retourne
  `{ isTrainingDay: <helper>({ retroactiveDone, hasPlanned, dayKey, todayKey }), isLoading: <OR des trois> }`.
  ⚠️ **Conflit de nommage** : le champ retourné s'appelle déjà `isTrainingDay` et le helper pur aussi →
  **aliaser l'import** (`import { isTrainingDay as computeIsTrainingDay } from '@wellness/shared'`) pour éviter
  la collision dans le corps du hook. Mettre à jour le JSDoc (« rétroactif **et** anticipé via le planning »).
- **UI** : **aucun changement** — `useNutritionSummary` et `(tabs)/nutrition.tsx` consomment `isTrainingDay`
  inchangé ; le badge existant s'affiche pour un jour anticipé comme pour un jour rétroactif.
- **React Compiler** : hooks inconditionnels (les 3 hooks appelés au même niveau) ; pas de mémo manuel.
