# Internationalisation & Traductions

> Plan de traduction de l'application. Complète [bonnes-pratiques.md](./bonnes-pratiques.md) (« aucune chaîne en dur, i18n dès le départ ») en décrivant **quelles langues**, **quoi traduire**, **comment** et **quand**.
> **Adapté à la décision G (04/07/2026) : FR + EN dès le lancement** — et non FR seul en V1 comme le prévoyait le cadrage Dams.
> Réf. : [architecture.md](./architecture.md) · [modele-donnees.md](./modele-donnees.md).

---

## 1. Principe

L'i18n n'est **pas** une fonctionnalité ajoutée après coup : tout est externalisé dès le départ. **Nouveauté par rapport au cadrage Dams** : la V1 sort en **français ET anglais** (décision G). Cela concerne trois surfaces à ne pas confondre :

| Surface | Exemple | Qui traduit | Où vivent les traductions |
|---|---|---|---|
| **UI statique** (chrome de l'app) | Boutons, libellés, erreurs, notifications | Équipe / traducteur | Fichiers de ressources `packages/shared/locales/` |
| **Contenu dynamique** (données) | Noms d'exercices, consignes, programmes, aliments, catégories | Back-office | Champs multilingues en base (tables de traductions) |
| **Bases externes** | Aliments CIQUAL, exercices importés | Import / traduction éditoriale | En base, par langue |

Le contenu **saisi par l'utilisateur** (aliments persos, notes de séance, exercices persos) n'est **jamais traduit** — il reste dans la langue de saisie.

---

## 2. Langues cibles & roadmap

| Langue | Statut | Justification |
|---|---|---|
| 🇫🇷 **Français** | **Lancement** | Locale source, marché initial, base CIQUAL en FR |
| 🇬🇧 **Anglais** | **Lancement** (décision G) | Ouverture internationale dès le départ — UI **et** contenu **et** bases |
| 🇪🇸 Espagnol · 🇩🇪 Allemand · 🇮🇹 Italien | Ultérieur | Selon la traction ; ajout purement éditorial une fois le pipeline validé |
| Langues RTL (arabe…) | Non planifié | Readiness prévue (§8), activation ultérieure |

**Décision** : le **français est la locale source**. Toute nouvelle clé est écrite en FR d'abord ; l'anglais en dérive **dans la même version** (plus de report en V2). Pas de clé qui n'existe qu'en anglais.

> Conséquence de la décision G : l'EN n'est plus un chantier de fin de projet. Le **bilingue FR+EN est intégré dans la charge de chaque version** (UI + contenu éditorial + bases), pas rattrapé après coup.

## 3. Stack technique i18n

| Brique | Choix | Rôle |
|---|---|---|
| Librairie | **i18next + react-i18next** | Chargement des ressources, changement de langue à chaud, namespaces |
| Détection locale | **expo-localization** | Langue + région du système au premier lancement |
| Format des messages | **ICU MessageFormat** | Pluriels, genre, sélection, interpolation typée |
| Formats nombres/dates | **`Intl`** (natif) | Séparateurs, dates, unités selon la locale |
| Stockage préférence | Settings utilisateur (SQLite + cloud) | Override manuel de la langue système, synchronisé |

- Les fichiers de traduction vivent dans **`packages/shared/locales/<lang>/<namespace>.json`** — partagés entre l'app mobile et le back-office.
- **Aucune chaîne en dur** : lint rule (`i18next/no-literal-string`) qui **fait échouer la CI** si une chaîne UI n'est pas passée par `t()`. Aligné avec la Definition of Done.
- La CI vérifie aussi que **les clés FR et EN sont synchronisées** (pas de clé orpheline, pas de clé manquante dans l'une des deux langues) — impératif direct de la décision G.
- Chargement **paresseux par namespace** (perf + poids de bundle).

### Structure des clés (namespaces)

```
common       → Boutons, actions génériques (Enregistrer, Annuler, Réessayer…)
auth         → Inscription, connexion, vérification email
onboarding   → Onboarding minimal + parcours guidé optionnel (décision F)
dashboard    → Blocs de l'accueil
muscu        → Suivi de séance, programmes, exercices
running      → Suivi GPS, types de séance, annonces vocales
nutrition    → Journal, macros, recettes
settings     → Profil, préférences, compte
errors       → Messages d'erreur (réseau, GPS, sync)
notifications→ Textes des push
units        → Libellés d'unités (kg/lb, km/mi, min/km)
```

**Convention de clé** : `namespace:section.element` (ex. `muscu:session.validateSet`, `errors:gps.unavailable`). **Jamais la phrase française comme clé** — une clé stable et sémantique.

## 4. Contenu dynamique — modèle multilingue

Les données de contenu gérées dans le back-office portent des champs **traduisibles** stockés par langue.

**Entités concernées**
- **Exercice** : nom, consignes techniques (muscles/matériel = enums → i18n côté UI, pas en base).
- **Programme** (muscu & running) : nom, résumé, description des séances.
- **Aliment** : nom (les valeurs nutritionnelles sont numériques, universelles).
- **Enums** (type de séance running, catégories d'aliments, groupes musculaires) → dictionnaire i18n côté UI.

**Approche en base** (voir [modele-donnees.md](./modele-donnees.md) §3.6) :

```
Exercise
  ├── id, difficulty, movement_type, equipment[]   (universel)
  └── translations[]
        ├── { lang: "fr", name, instructions }
        └── { lang: "en", name, instructions }     ← rempli dès le lancement (décision G)
```

- **Table de traductions liée** (`exercise_translations`, `program_translations`, `food_translations`) plutôt que colonnes par langue — extensible sans migration à chaque nouvelle langue.
- **Fallback** : si la traduction manque dans la langue de l'utilisateur → on sert le **FR** (locale source), avec un marqueur discret « non traduit » côté admin.

**Sources de données externes (bilingues dès le lancement, décision G)**
- **CIQUAL** (aliments bruts) : FR uniquement à l'origine → **noms EN à produire dès la V1** (traduction éditoriale ou mapping USDA) — c'est un livrable de contenu de la V1, pas un report.
- **OpenFoodFacts** : **déjà multilingue** (`product_name_fr`, `product_name_en`…) → import des deux langues, fallback sur le nom générique.
- **Base d'exercices** (`exercises-dataset`) : instructions **FR + EN déjà fournies** → import direct des deux langues.

## 5. Formats & conventions locales

Traduire ne suffit pas : il faut **localiser** les formats. Découplé du choix de langue.

| Élément | FR (défaut) | EN / US | Source |
|---|---|---|---|
| Séparateur décimal | `1 840,5` | `1,840.5` | `Intl.NumberFormat` |
| Unités de poids | kg | lb (si impérial) | conversion à l'affichage |
| Distance | km | mi (si impérial) | conversion à l'affichage |
| Allure running | min/km | min/mi | dérivé de l'unité de distance |
| Dates | `04/07/2026` | `07/04/2026` | `Intl.DateTimeFormat` |
| Premier jour de semaine | lundi | dimanche (US) | calendrier dashboard & planning |
| Calories | kcal | kcal / Cal | libellé i18n |

> ⚠️ Le **choix d'unités (métrique/impérial) est indépendant de la langue**. Un anglophone peut être en métrique. Ne jamais coupler `lang === 'en'` avec `units === 'imperial'`.

## 6. Cas particuliers

### Annonces vocales running (TTS)
- Guidage fractionné et annonces au km en **text-to-speech** → doivent parler la **langue de l'app**.
- `expo-speech` avec la voix de la locale ; textes dans le namespace `running`. Textes **FR et EN** prêts dès le lancement.
- Vérifier la prononciation des nombres et unités (« 3 kilomètres, allure 5 minutes 20 » / « 3 kilometers, pace 5:20 »).

### Pluriels & genre
- Passer par **ICU** : `{count, plural, one {# série} other {# séries}}` — jamais de concaténation manuelle.

### Notifications push
- Générées côté serveur mais **rendues selon la langue de l'utilisateur** (stockée dans son profil, synchronisée) → le backend a accès aux fichiers de `packages/shared/locales`.

### États vides, erreurs, onboarding
- Écrans à fort volume de texte → à externaliser (FR + EN) dès l'écriture, pas en rattrapage.

---

## 7. Sélection & détection de la langue

- **Premier lancement** : langue = locale système (`expo-localization`) si supportée (FR ou EN au lancement), sinon FR.
- **Override manuel** : sélecteur dans Paramètres → Préférences → Langue.
- **Changement à chaud** : pas de redémarrage (react-i18next re-render).
- La langue choisie est **synchronisée** (settings cloud, via PowerSync) pour être cohérente entre appareils et pour les notifications serveur.

---

## 8. Readiness RTL (droite-à-gauche)

Non activé, mais **anticipé** pour éviter une refonte :
- Propriétés logiques (`marginStart`/`marginEnd`, pas `left`/`right`).
- Ne jamais coder en dur l'alignement du texte.
- Icônes directionnelles à miroir automatique.

---

## 9. Workflow de traduction

1. **Écriture** : le développeur ajoute la clé **en FR** dans le namespace concerné, **et sa traduction EN** dans la même PR (décision G).
2. **CI** : la lint rule vérifie qu'aucune chaîne n'est en dur **et** que les clés FR/EN sont synchronisées (échec CI sinon).
3. **Traduction UI** : outil de gestion à choisir (Weblate self-hosted, Crowdin, ou PR sur les JSON).
4. **Contenu** : le back-office affiche pour chaque exercice/programme/aliment un **onglet par langue** (FR + EN) avec indicateur « traduit / non traduit » ; fallback FR tant que la traduction manque.
5. **Revue** : relecture par un locuteur natif avant publication (contenu) / release (UI).

---

## 10. À retenir

- L'i18n est **structurelle** : externalisation dès le début, coût quasi nul si fait dès le départ.
- **FR + EN dès le lancement** (décision G) : UI, contenu éditorial **et** bases (dont traduction EN de CIQUAL) sont livrés bilingues dès la V1, intégrés à la charge de chaque version.
- **Trois axes indépendants** : langue ≠ unités ≠ région.
- **Français = locale source** ; rien dans le code ne change pour ajouter une 3ᵉ langue plus tard — seulement remplir des fichiers et des champs.
