Archivage sûr du contenu éditorial

Aujourd'hui, archiver un exercice est une porte à sens unique qui efface son nom de l'historique de tous les utilisateurs. Cette US ajoute trois choses : savoir ce qu'on casse avant d'archiver, revenir en arrière, et surtout arrêter de casser l'historique. Recette navigateur, aucun APK requis.

La chaîne de défaillance actuelle

Admin archive « Développé couché » → deleted_at = now → sync rule filtre deleted_at is null → la ligne quitte les appareils → l'historique affiche un nom VIDE
  • workout_sets ne porte que exercise_id — aucun nom dénormalisé.
  • Le repli du mobile est la chaîne vide (workout-repository.ts:225) : pas de message, pas d'erreur, du vide.
  • Et aucune restauration n'existe côté admin : le contenu archivé disparaît de l'admin lui-même.

3 · Le correctif qui compte (D2)

Ce qui change dans la sync rule

  • shared_content cesse de filtrer deleted_at is null sur les tables éditoriales.
  • Le contenu archivé reste sur les appareils → l'historique résout son nom, même hors ligne.
  • Le masquage passe dans l'app, là où il relève de l'usage : les listes de sélection ajoutent deleted_at IS NULL, les résolutions de nom non.
  • ⚠️ Sync rule à redéployer à la main sur l'instance PowerSync.

Pourquoi pas dénormaliser le nom

  • Il faudrait une migration et un remplissage rétroactif de workout_sets et food_entries.
  • Surtout : ça fige le nom. Une faute d'orthographe corrigée ou une traduction améliorée ne remonterait plus jamais dans l'historique.
  • Ça règle le symptôme en créant une seconde vérité.

🐛 Trouvé au cadrage — l'import CSV (D7)

  • L'import fait upsert(..., { onConflict: 'import_key' }) et import_key est unique.
  • Ré-importer un CSV contenant un aliment archivé met à jour la ligne sans remettre deleted_at à null.
  • Résultat : l'aliment reste invisible partout, et le rapport annonce un succès. L'admin croit avoir réimporté, il n'en est rien.
  • → L'import doit réactiver et l'annoncer : « 4 aliments archivés réactivés ».

Où est le vrai risque

  • Pas dans l'admin : l'archivage n'est pas réécrit, on ajoute le décompte devant et la restauration à côté.
  • Dans l'app : après le changement de sync rule, toute requête de sélection oubliée proposerait un contenu archivé.
  • Parade : recensement écrit et traitement requête par requête, pas une relecture rapide.
  • Et une vérification préalable : la RLS admin autorise-t-elle le décompte inter-utilisateurs ? Sinon, fonction security definer → migration.
